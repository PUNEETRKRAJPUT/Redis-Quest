## Exact payloads
`service_scaled` (engine `level.event`, ring and WebSocket):
```json
{ "kind": "service_scaled",
  "data": { "service": "app", "instances": 2, "previous": 1, "ids": ["2f03e4f55e5e", "e6bcc58ad141"] } }
```
`ids` is the sorted list of live instance ids after the change. A level matches it with
`kind: service_scaled, match: { service: app, instances: 2 }` (`eventMatches` looks `match` keys up on `data`; numbers go
through `looseEqual`). The first push after boot emits `instances: 1, previous: 0`; the last instance going quiet emits
`instances: 0`. A change of ids with the same count does not emit.

## Route contract
`POST /api/levels/:id/slots`, body `{ "active": boolean }`.
- 404 `no_player` / `unknown_level`; 409 `level_locked`; 409 `level_not_started` unless the level is `in_progress` or
  `passed` (`activeEntry`, same as brainstorm); 400 `invalid_active` when `active` is not a boolean.
- 409 `verify_in_progress` while a verification runs for the player (the route takes the verifier's per-player guard,
  `verifier.begin`, for the duration of the change, so it also cannot race a verify that starts at the same moment).
- `own = levelSlots(verify)` (the slots the level's behavior-shaped verifiers name). `true`: active list becomes the union of
  the current list and `own` (order: current first, then new). `false`: `own` is removed. Applied exactly like `PUT /api/slots`
  (`runtime.activeSlots`, then `commit('slots', ...)` which persists and tells the WebSocket).
- Response `200 { "active": string[], "own": string[] }`.

`GET /api/levels/:id` gains `slots: { own: string[], active: boolean }`. `active` is true when `own` is non-empty and every own
slot is in the current list. Levels without slots: `{ own: [], active: false }`.

## Harness rules as implemented (`scripts/grade/grade.mjs`)
All three apply only to solutions declared `right` or `works_but_wrong`; a `wrong` one gets nothing. Levels without these event
kinds take the same path as before (`verifyWithEvents` falls through to the old `verify()`); the example levels graded unchanged.
1. `service_scaled` with `match.instances: N`: wait until `grader-instance-2` from a previous good solution has expired (8 s after
   its last push), read `GET /api/metrics?seconds=5`, POST `/internal/metrics` 3 times one second apart (`instance` and
   `instanceId` `grader-instance-2`, `routes: {}`, `windowMs: 1000`, `at` floored to the second), then read `GET /api/events` and
   put one line in the row's note: either "engine emitted service_scaled instances N" or a `NOTE service_scaled: ...`.
2. `channel_message` with `match.channel`: `verify()` is started without awaiting; a listener on the WebSocket's `verify_*` events
   waits for `verify_check_started` with that verifier's `index` and the level id, publishes through `/api/cli` after 300 ms and
   then once a second (cap 10) until `verify_check_finished` for the index. Message is `match.message` if present (a non-string is
   JSON-stringified; templates rendered), else `{"matchId":"m-041","seq":1,"over":1,"ball":1,"runs":4,"batter":"p-028"}`. Several
   channel verifiers on one level each get their own publisher.
3. custom `ticker_gap`: PUBLISH `score:match:m-041` seq 1; POST `/app/ticker/resubscribe {matchId, pauseMs: 1000}` not awaited;
   200 ms; PUBLISH seq 2, 3; await the resubscribe; PUBLISH seq 4. A 404 prints and records
   `NOTE ticker_gap: /app/ticker/resubscribe not available (A-02 not merged)` and the harness carries on.

## Did the engine see the fake instance while a real app also pushes?
Yes. In the check the stack has one real app instance (after the scale test) pushing heartbeats; the fake pushes took the
engine from 1 to 2 live instances and it emitted `service_scaled` `instances: 2, previous: 1, ids: [<real>, grader-instance-2]`
(the grading line says so). Caveats, documented in `docs/grading.md`: the stack must have exactly N-1 real instances (with two
real app instances the fake one makes three and no `instances: 2` event happens, and the harness prints a NOTE); the "instances
the engine already knew" list in the note comes from `GET /api/metrics`, which keeps an instance for 5 minutes, so it can show a
scaled-down instance that is no longer live.

## What surprised me
- Timing in the check is real: the first `service_scaled instances 2` event appears within a second of the engine starting
  (both instances push within a second of each other), so the 15 s allowance is generous.
- The channel check for a good solution passes with one PUBLISH (the first one at +300 ms lands after SUBSCRIBE); the cap of 10 is
  only a guard.
- A reference `.js` that publishes inside the function (as the spec describes level 02) does not help the verifier: the function
  runs in the runner before the engine's check SUBSCRIBEs. The harness's publisher is what makes it pass. Chapter 3 level authors
  must know this: a level that waits on a message cannot rely on the learner's own function publishing during the behavior check.

## What the next agent must know
- Chapter 3 levels use `kind: service_scaled, match: { service: app, instances: 2 }` for "you are not alone", and
  `kind: channel_message, match: { channel: ..., message?: ... }` for pub/sub levels. Keep `timeoutMs` generous: G-01's override caps
  waits at 3 s (`VERIFY_MAX_EVENT_WAIT_MS`) and the harness publishes 300 ms after the check starts.
- A scale event from earlier in the session already counts: the verifier looks back to the level's `startedAt`, so a learner who
  scaled before pressing Verify passes, and a learner who scales to 2 and back to 1 before starting the level does not.
- `engine/test/verify-slots.test.ts` compares the engine's slot table with the app's registry; it is A-02's to keep green.
