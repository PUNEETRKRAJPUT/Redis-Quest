# G-01 handoff: level grading harness

## What I did
- `scripts/grade/grade.mjs` (ESM, Node 24) and `scripts/grade/grade.sh` (bash 3.2 wrapper; builds `@quest/shared` if
  `packages/shared/dist` is missing). Levels are read with `loadChapter`, `renderTemplate` and `resolveLevelPath` from the
  built `@quest/shared`; no YAML is parsed by the tool.
- `scripts/grade/compose.g01.yaml`: compose override for the check (own image tag `quest-g01-node`, scratch workspace, logs,
  progress and levels, live `scenarios/` mount, event waits capped at 3 s so wrong event solutions grade fast). It replaces
  the P0-09 override; the app keep-alive workaround is not needed any more (F-01), and none was set.
- `scripts/grade/known-content-bugs.tsv`: mismatches the check prints as `CONTENT-BUG` (still exit 1).
- `scripts/check/G-01.sh`: project `quest-g01`, `.env.g01` (copied from `.env.p09`, ports forced to 3500/6395/5437/5545,
  `ENGINE_DEV=1`), no insight, scratch copy of `_examples/example-*`, `ch0-boot`, `ch1-keyspace`, `ch2-everyone-showed-up`
  under `logs/.g-01-check`, image build retried 3 times, `docker compose -p quest-g01 down -v` on exit.
- `docs/grading.md`: how to use the tool while writing content.
- Did not touch engine, app, runner, ui, packages, levels, other checks, `docs/BUILD.md`. No git add/commit.

## Usage
```
scripts/grade/grade.sh [--engine http://127.0.0.1:3500] [--workspace DIR] [--levels DIR] [--run-ops] [--json FILE] <chapter-dir | level-id>...
```
Exit 0 no mismatch, 1 at least one MISMATCH, 2 the tool could not run. The engine must mount the same level files and run
with `ENGINE_DEV=1` (the tool completes earlier levels through `POST /api/levels/:id/complete` to unlock the one it grades).
See `docs/grading.md` for the rules per solution type.

How each solution is played: `start` (re-runs `setup`), then `.redis` lines through `/api/cli` (templates rendered), or the
`.js` copied to the slot's workspace file (`PUT /api/workspace/file`; slot-to-file read from `GET /app/slots`, table fallback
from P0-07) with the engine activating the slot during `/verify`, or `.sh` SKIPPED unless `--run-ops`. `answer` verifiers get
the live reply of `expected.cmd` (declared right or works_but_wrong) or `not-the-answer` (declared wrong); `quiz` gets the
correct or a wrong option the same way; decision levels use the reference options, and each wrong entry swaps in its one option.
`event`: `cli_ping` comes from PING, `ui_connected` is posted as the UI does, and for `progress_restored` the harness only calls
`POST /api/progress/restore` (it does not post the event itself, which is how the missing emitter below shows). A solution that
ran FLUSHALL or FLUSHDB is followed by a restore. Code slot files are put back after each level. Progress lines (baseline,
load run, "still verifying") come from the engine's WebSocket `verify_*` events.

## Content bugs found (none edited)
1. **ch1-01-a-name-and-an-otp, `01-wrong-name-under-another-key.redis`: declared wrong, engine right.** The level has no
   `setup`, so `user:<id>:name` and `otp:<id>` from the reference run are still in Redis when the wrong solution runs, and all
   three checks pass. Engine feedback: none (`All 3 checks passed.`). Fix: add `setup` with `DEL user:{{player.id}}:name
   user:{{player.id}} otp:{{player.id}}`. A learner who retries the level hits the same leftover state.
2. **ch1-13-the-player-card, `13-reference.redis`: declared right, engine wrong.** Feedback: `The tags array should hold two
   tags, hot and top-pick. Use JSON.ARRAPPEND on $.tags. (expected something matching /2/, got [2])`. `JSON.ARRLEN ... $.tags`
   replies with a list (`[2]`) and `matches` only accepts a string reply (`engine/src/verify/assert.ts`). Fix: `equals: [2]`
   or an unwrapped path. The correct tags, nested and role checks already pass.
3. **ch1-15-roommate-cleaned-up, `15-reference.redis`: declared right, engine wrong (engine/UI gap, level is fine).** Feedback:
   `The game has not seen a restore yet. Run FLUSHALL, then accept the game's offer to restore your progress from the snapshot.
   (nothing since the level started, and nothing in 3 s of waiting)`. The `redis` check passes (the restore ran). Nothing emits
   custom event `progress_restored`: `POST /api/progress/restore` in `engine/src/server.ts` only emits `progress.changed`, and
   `ui/src` does not post it, although `docs/specs/C1-chapter-1.md` says the engine does. Real learners cannot pass this level
   until the engine (or UI) emits it. Not fixed here (engine is not mine).

The check prints these three as `CONTENT-BUG` lines and exits 1. Delete a line from `known-content-bugs.tsv` when its bug is
fixed; when all three are, the check should exit 0.

## What I did not do / limits
- `.sh` ops solutions are not executed (ch0-01, ch0-04, ch0-05 and `example-ops`: 8 SKIPPED rows). `--run-ops` runs them on
  the Mac against the default compose project; never used by the check. Consequently the ch0-04 answer (TTL) and the ch0
  event-after-restart behaviours that P0-09 simulated are not exercised here.
- No extra probes (empty file, TODO stub, "no answers") beyond what each level declares; P0-09 covers those for the examples.
- Wrong solutions get wrong answers and wrong quiz picks by design (spec), so a wrong solution whose only flaw is a missing
  answer grades `wrong` through the answer, not through its own `redis` checks.
- Traffic levels (ex-code-01, ch2-02, ch2-04) ran through the real baseline and load run (a few minutes in total).

## Surprises
- The grader is only as honest as `setup`: state left by an earlier solution is visible to the next (bug 1). The engine does
  not wipe the keyspace between solutions, and should not.
- `curl`-style host access works now (the proxy publishes 3500); the engine itself has no host port, everything goes via Caddy.
