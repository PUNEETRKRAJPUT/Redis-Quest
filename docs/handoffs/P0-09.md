## Verify response as built (`POST /api/levels/:id/verify`, body `{ answers?: { "<index>": string | string[] } }`)
```
{ verdict: 'right' | 'works_but_wrong' | 'wrong',
  levelId, attempt, startedAt: iso | null, durationMs,
  checks: [ { index, type, ok, message, details, durationMs, skipped? } ],   // in verify-list order
  metrics?: { index, scenario, connections, durationSec, capped, levelSlots, baseline?, run, assertions },
  attempts, status,                                                        // added by the route
  ideal? }                                                                 // when allowed, see below
```
- `index` = position in the level's `verify` list (same as the level payload and `answers`).
- `ok:false` on `type: antipattern` is a hit: `message` is the works-but-wrong feedback.
- `message` is one or more lines (`\n`): one line per failing sub-check. Passing messages are fixed strings (below).
- `skipped: true` only for a traffic verifier not run because the verdict was already wrong.
- `details` per type: redis/antipattern checks `{ items: [{ cmd, ok, expected, observed, feedback }] }`;
  behavior `{ slot, module, fixtures: { file, steps }, concurrency, assertions: [{ call, repeat, ok, feedback,
  returnedMatching?, errors, firstError?, sideEffects?, ms }] }`; event `{ kind, match, how:
  already_happened|arrived|timeout, waitedMs, since, event? }`; quiz `{ question, picked, explanation? }`
  (explanation only when correct); answer `{ prompt, typed, cleaned, compare, transform }` (never the expected
  value); traffic `{ scenario, connections, durationSec, capped, levelSlots, baseline: { recordedAt, reused,
  recordedBecause?, run }, run: { load, app }, assertions: [{ key, ok, value, needs, text }] }`.
- `progress.json` `levels[id].verdicts[]` entries are now `{ at, verdict, durationMs, checks: [{ index, type, ok, skipped? }] }`;
  `levels[id].idealRevealedAt` is set the first time the ideal is served.
- WebSocket: `level.event` with `kind: custom` and `name` `verify_started` `{ levelId, attempt, total }`,
  `verify_check_started` `{ levelId, index, type }`, `verify_check_finished` `{ levelId, index, type, ok, skipped? }`,
  `verify_traffic_phase` `{ phase: baseline|run, scenario, activeSlots }`, `verify_finished` `{ levelId, verdict, durationMs }`.
- 409 `{ error: 'verify_in_progress' }` when the same player verifies while a verification (or a baseline refresh) runs.

### The ideal way (for P0-10's follow-up)
`ideal` is in the verify response when allowed: level `passed`, or `attempts >= 3` (counted after this attempt).
`GET /api/levels/:id/ideal` (level not locked) always returns it plus `{ allowed, reason }`; both record `idealRevealedAt`.
```
file modes: { mode: 'cli'|'code'|'ops', reference: { path, content }, wrong: [{ path, content, expect, because }], reasoning }
decision:   { mode: 'decision', reference: { options: [ids] }, quizzes: [{ index, question, correct: [ids], explanation }],
              wrong: [{ option, expect: 'wrong', because }], reasoning }
```
`.redis` content is templated (player id filled in); `.sh` and `.js` are shown as written. `reasoning` = the reference
file's own comment lines, then "Why the others fall short:" and `- <path> (<expect>): <because>` per wrong solution
(decision: the explanations, then `Not <option>: <because>`). `reason` strings: `You passed this level.`,
`Shown after 3 attempts (N so far).`, `Not passed yet, and N of 3 attempts used. You can still reveal it.`

## Order and skip rules
- Verifiers run in list order, except **traffic verifiers run after all others** (coordinator rule from P0-07: learner
  code runs in-process in the app, where a synchronous infinite loop cannot be stopped, so it must first pass its
  behavior verifiers in the runner). Once the verdict is already `wrong` (any non-antipattern failure, e.g. behavior
  failed) a traffic verifier is **skipped** and the slot is never activated in the app. Event checks then only look back
  (no wait). Results are reported in list order.
- Slot activation is only for the level's slots, = every `slot` named by its behavior or behavior-shaped antipattern
  verifiers. A traffic-only level activates nothing (it grades the app as it is). Authors: give every slot a traffic
  verifier depends on a behavior verifier.

## Scenario file format
See `scenarios/README.md` (copied here in short): `{ id, description?, durationSec, connections, pipelining?=1, seed?=1,
warmup?: { durationSec, connections }, users: { count, distribution: uniform|zipf, zipfSkew?, idPattern?="u-{n}", pad?=6 },
params?: { <name>: { values, distribution, zipfSkew? } }, requests: [{ method, path (/app/...; {user}, {<param>}),
weight?=1, userIdHeader?, body? }] }`. Additive to the spec: `seed`, `warmup`, `params`, `idPattern`, `pad`, `body`.
Paths are absolute from the proxy origin and must start with `/app/`.

## Baseline semantics as implemented
- `baseline: true`: before the graded run the engine needs a baseline for the scenario. It reads
  `${PROGRESS_DIR}/baselines/<scenario>.json` and reuses it only if its fingerprint matches: scenario content hash,
  active slots during the baseline (= currently active slots minus the level's slots), `dbExtraLatencyMs`, effective
  connections and duration (after caps), `APP_URL`. Otherwise it records a new one: `PUT /api/slots` to that set, wait until
  `/app/health` reports it 4 times in a row (12 s timeout), warmup (discarded), 3.2 s quiet, measured run, 2.5 s for the
  last metric push, then stores `{ version, scenario, recordedAt, fingerprint, run: { load, app } }`. A baseline with no
  2xx or an error rate above 50% is refused (never stored) and the verifier fails with that reason.
- Graded run: slots = currently active ∪ level slots, same warmup/measure. Afterwards the original active set is restored.
- `POST /api/baselines/:scenario/refresh` body `{ levelId? }`: re-records; with `levelId` the level's slots are off and the
  rest stay; without it every slot is off. Returns the record. 409 while a verification runs.
- Ratios: `p99_ratio_lte` = run p99 / baseline p99 (autocannon, client side); `rps_ratio_gte` = run rps / baseline rps;
  `db_calls_ratio_lte` = (Postgres queries per app request in the run) / (same in the baseline). **Per request, not totals**:
  totals in a fixed time are confounded by throughput (a faster app makes more requests and so more total calls).
  `hit_ratio_gte` = noDbCount / requests (app metrics); `error_rate_lte` = (5xx + no response) / attempts;
  `db_queries_lte` = total Postgres queries in the window; `p99_ms_lte` = run p99.
- Implicit guard: with no `error_rate_lte`, a run with more than 1% errors fails ("a fast error is not a fast page");
  a run with zero 2xx always fails; missing app metrics fail the db/hit assertions (never pass them).
- Not in the fingerprint (recorded only): number of app instances, app env. A scaled app or a changed app config reuses an
  old baseline unless something in the fingerprint changed; refresh explicitly.

## Caps
`LOAD_MAX_CONNECTIONS` (200), `LOAD_MAX_DURATION_SEC` (30), `LOW_POWER=1` halves both; applied to the run and the warmup;
`details.capped` says which applied. **docker-compose.yml does not pass these to the engine yet** (its environment block is
fixed), so in the default stack only the defaults apply; request: add `LOAD_MAX_CONNECTIONS`, `LOAD_MAX_DURATION_SEC`,
`LOW_POWER` (and optionally `VERIFY_MAX_EVENT_WAIT_MS`) to the engine's environment. Other caps: behavior concurrency is
clamped to the runner's 200 (`details.concurrency`); runner timeout per assertion = min(60 s, 10 s + 200 ms x ceil(repeat/concurrency)).

## Exact feedback strings (what a level author can rely on)
Failing redis / antipattern check: `<message> (expected <E>, got <O>)`; without a message: `<CMD args>: expected <E>, got <O>`.
`<E>` per assertion: equals `v` -> `<v>`; notEquals -> `anything but <v>`; gte -> `at least <n>`; lte -> `at most <n>`;
between -> `between <a> and <b>`; exists true -> `a value (not nil, not an empty list)`, false -> `nil or an empty list`;
matches -> `something matching /<re>/`; oneOf -> `one of <a>, <b>`; lengthGte -> `length at least <n>`;
contains -> `something containing <v>`. `<O>`: the reply rendered (`nil`, `150`, `zset`, `[a, b]`, `(empty list)`,
`""`, strings over 120 chars cut with `…`, lists over 10 shown as `… (+N more)`); for lengthGte `length <n>`; non-numeric for
gte/lte/between: `<reply> (not a number)` or `a list [..]`; error reply: `an error: <redis error>`; Redis down:
`no reply (Redis is not reachable right now)`. Refused write: `<message> (<CMD> is not on the read-only allowlist, so the
engine refused to run it (a verifier must not change your data))`.
Passing: redis `The check passed.` / `All N checks passed.`; antipattern `No antipattern found.`
Behavior (base = assertion `message`, else the behavior verifier's `message`, else `<slot>(<args json>)`): `<base> (<detail>)` with
detail one of `expected <json>, got <json>[ on call i of n]`, `expected exactly|at least|at most|between a and b <k> of <n>
calls to return <json>, got <m>`, `the call threw: <Name>: <msg>`, `<f> of <n> calls threw; the first: <Name>: <msg>`,
`your file could not be loaded: <msg>` (module errors), `it did not finish in time (<msg>)`, `expected it to throw, but it
returned <json>`, `expected an error matching /<re>/, got <Name>: <msg>`, `the runner that calls your function is not
reachable: <msg>`. Side effect without its own message: `<base> (after the call, <CMD>: expected <E>, got <O>)`; with one:
the redis-check format. Fixtures failure: `The engine could not reset this level's state before calling your function (<why>).`
Passing: `The assertion held.` / `All N assertions held.` (behavior-shaped antipattern: `No antipattern found.`).
Unknown slot: `The engine does not know which workspace file implements slot <slot>.`
Event fail: `<message or "The game has not seen <thing> since you started this level."> (nothing since the level started, and
nothing in <s> s of waiting)` or `(not waited for: an earlier check already failed)`. Pass: `The game saw <thing> at <iso>.` /
`The game saw <thing> while it waited.`
Quiz: `Correct. <explanation>`; `Not quite: you picked "<label>".` (+ ` This question has N correct options.`);
`No answer was submitted for this question.`; `<id> is not one of the options for this question.`
Answer: `Correct.`; `<message> (you typed "<text>")`; `<message> (nothing was typed)`; `<message> (you typed "<text>"; Redis has
no value to compare it with right now)`; `<message> (could not read the expected value: <why>)`. Typed answers are trimmed,
`(integer) ` and one pair of surrounding double quotes are stripped (redis-cli copy-paste).
Traffic: pass `Passed under load: <parts joined by "; ">.`; fail `<message or "Under load the app did not reach the target."> (<failed
parts>)`, parts like `p99 ratio 0.83 (412 ms now vs 496 ms baseline), needs at most 0.2`, `Postgres calls per request ratio 1 (1 per
request now vs 1 baseline), needs at most 0.1`, `cache hit ratio 0.5 (50 of 100 requests skipped Postgres), needs at least 0.9`,
`error rate 2% (20 5xx, 0 without a response), needs at most 0`, `3% of requests failed (...); a fast error is not a fast page`,
`<n> Postgres queries during the run, needs at most <k>`, `p99 <ms>, needs at most <k> ms`. Skipped: `Skipped: another check
already failed, so the load test was not run (your code is only put into the app once it passes in the runner).`
Engine error inside one verifier: `The engine could not run this check: <msg>` (that verifier fails; others still run).

## What surprised me (and what needs fixing elsewhere)
1. **App keep-alive breaks every cached load test (P0-07).** The app defaults to `APP_MAX_REQUESTS_PER_SOCKET=1`
   (`Connection: close` after each response, so Caddy redials and spreads across scaled instances). At ~2,000 req/s Caddy
   fills its ephemeral port range (28,231 sockets in TIME_WAIT seen) and answers **502 "dial tcp ...:4000: connect: cannot
   assign requested address"**: 13.5% 5xx in the graded run, so the reference cache-aside failed honestly ("a fast error is
   not a fast page"). My override sets `APP_MAX_REQUESTS_PER_SOCKET=100` for the check only; then the reference passes
   (p99 20 ms vs 3,663 ms). The default stack needs a real fix (e.g. a larger value in compose, or Caddy dynamic upstreams
   with per-request balancing and keep-alive). Until then learners' correct caches will fail traffic verifiers.
2. **ch0-05 and example-ops cannot pass with the current compose.** Redis runs with `--save "" --appendonly no`; after
   `docker compose down` + up, Redis is empty (`DBSIZE 2`, boots = 1, save file gone). After `POST /api/progress/restore`
   boots is written back from engine memory (1), so `GET game:engine:boots gte 2` still fails. example-ops' `redis_reconnect`
   event can never be seen because the engine restarts too. Either persistence on for `redis`, or the engine keeps the boot
   count in progress.json and restores max(file, live), or the level checks something else. (The UI agent reported all five
   ch0 levels `right`; if it restarted only some services, Redis would have kept its data. Worth checking which.)
   `down` and `down -v` are indistinguishable for Redis today, so ch0-05's wrong solution teaches something the stack does not do.
3. **example-code-01's works_but_wrong is unreachable (P0-05 example).** Its behavior verifier's side effect `TTL between [1, 30]`
   fails a no-TTL cache first, so the verdict is `wrong`, never `works_but_wrong`. Fix: drop the TTL side effect from the
   behavior verifier (keep it in the antipattern), or make it `TTL notEquals -2`.
4. `GET /api/metrics` dropped `dbQueries`/`redisCommands`; fixed in `metrics.ts` (sums) with the coordinator's OK.
5. The engine's 200-event ring is shared with verify progress events; the verifier keeps its own log (2,000 events + latest per
   kind/name/payload) and ignores `verify_*` names, so Chapter 0's "already happened" cannot be evicted by verify attempts.
   Authors: do not name custom events `verify_*`.
6. The `ideal` and slot table for decision levels read only the parsed level: `.redis` content is templated; `.js`/`.sh` not.
7. Scenarios are baked into the image at build time (`COPY scenarios`); the check mounts `./scenarios` live. Consider the same
   mount in docker-compose.yml so a scenario edit does not need a rebuild.
