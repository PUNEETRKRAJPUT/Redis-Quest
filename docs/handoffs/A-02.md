|---|---|---|---|---|

| `leaderboard.rank` | `ch3/leaderboard-rank.js` | `(deps, contestId, teamId)` | `{ rank (integer, 1 = best), score (number), around: [{ teamId (string), score (number) }] }` or `null` (404); `around` is up to two above and two below plus the team, best first | window function `row_number() OVER (ORDER BY points DESC, id)` over the whole contest, then `rn BETWEEN me-2 AND me+2` |

| `contest.join` | `ch3/contest-join.js` | `(deps, userId, contestId, fee)` | strictly `true` (fee taken) or `false` (balance too low, route 402); `1`/`undefined` is a 500 `SlotContractError` | one guarded `UPDATE wallets ... WHERE balance >= $2 RETURNING` plus the ledger insert in a single data-modifying-CTE statement |
| `ticker.publish` | `ch3/ticker-publish.js` | `(deps, matchId, ball)` | anything (echoed as `result`; natural value is the PUBLISH receiver count) | no-op returning `0`, publishes nothing |

- `leaderboard.top` (`ch3/leaderboard.js`, `(deps, contestId, limit)`) is unchanged; `GET /app/leaderboard/:contestId` and
  `GET /app/limits/ping` are untouched.
- `rows` for `leaderboard.recompute`: `[{ contestId: number, teamId: string, points: number }]` (`contest_id` is a Postgres bigint and is
  converted with `Number`; `teamId` is the bigint `fantasy_team_id` as a string; `points` is `numeric(8,1)` converted with `Number`). The
  SELECT is exactly the spec's, no ORDER BY.
- `contest.join` baseline is one statement, not BEGIN/COMMIT: `LearnerDeps.db` is `{ query }` over a pool, so there is no way to hold a
  connection for a transaction. A single statement is atomic, the UPDATE row lock makes concurrent debits queue and re-check
  `balance >= fee`, and the ledger row is inserted `FROM` the rows the UPDATE changed, so a refused debit leaves no trace. Ledger row:
  `delta = -fee`, `reason = 'contest_entry'` (the seed's own reason string), `ref = '<contestId>'`, `created_at = now()`. An unknown user
  has no wallet row and gets `false` (402), not 404.
- Rank ties break by entry id in the baseline; a sorted set breaks them lexicographically by member, so a learner's ranks can differ from
  the baseline's inside a tie. The reference fixtures and the check use ids and scores without ties where it matters.

## The ticker (provided subscriber, `app/src/workers/ticker.ts`)
- Per instance, own connection, `disableOfflineQueue`, same reconnect policy as the change consumer. At boot it reads
  `SELECT id FROM matches WHERE status = 'live' ORDER BY id` **once** (retrying every second until Postgres answers, because the seed
  can still be loading) and `SUBSCRIBE`s to `score:match:<id>` by exact channel (m-041 and m-042 in the seed). A match that turns live
  later is not picked up until the app restarts. If the engine switches the Redis target, the client is rebuilt and resubscribed; state is kept.
- Channel message: a JSON object with an **integer `seq`**. The reference publisher sends `{ ...ball, matchId }`, e.g.
  `{"seq":1,"over":1,"ball":1,"batter":"p-028","runs":4,"matchId":"m-041"}`. Anything that is not JSON, not an object, or has no integer
  `seq` is `malformed`.
- `GET /app/ticker/:matchId` answers
  `{ matchId, subscribed, received, lastSeq, last, recent, gaps, malformed, instance }`:
  - `received` counts **every** message, malformed ones included; `malformed` counts the bad ones too.
  - `lastSeq` / `last` are the `seq` and body of the most recent **well-formed** message (null before the first). `lastSeq` is assigned,
    not max-ed, so a publisher that restarts at seq 1 simply continues from there with no gap.
  - `recent` is the last 20 well-formed messages, oldest first.
  - `subscribed` is true while the connection is ready and the channel is subscribed (false during a resubscribe pause).
- Gap rule: while `lastSeq` is known, a well-formed message with `seq > lastSeq + 1` is a gap: `gaps += 1`, one warn log line, and a fire
  and forget `POST ${ENGINE_URL}/api/events` (3 s timeout, one warn line on failure) with
  `{ "kind": "custom", "name": "ticker_gap", "data": { "matchId", "instance", "expected": lastSeq + 1, "got": seq, "missed": seq - lastSeq - 1 } }`.
  The engine records it as `{ at, type: "level.event", data: { kind: "custom", name: "ticker_gap", data: {...} } }` on `GET /api/events`
  (seen in the check: `{"matchId":"m-041","instance":"6923e3e0b49e","expected":2,"got":4,"missed":2}`). `seq <= lastSeq` is not a gap.
- `POST /app/ticker/resubscribe` UNSUBSCRIBEs the channel on this instance (the connection stays up), waits `pauseMs`, SUBSCRIBEs again
  and answers only after Redis confirmed the new subscription. `PUBLISH` during the pause returns 0 receivers (measured).
  With two instances the call only affects the instance that answered; the proxy picks it.

## Measured facts for the level authors
Row counts for `POST /app/leaderboards/recompute` (the live seed, quest-a02):
- `m-001` alone: **4827** rows. `m-001` .. `m-008` together: **40098** rows (the level wants about forty thousand, so use the eight).
- Slot time with the pipelined reference learner (`multi()` + `execAsPipeline()`, batches of 5000, one `ZADD` per row): 30 to 37 ms for 4827
  rows and 121 to 124 ms for 40098 rows on this Mac (two runs; not a benchmark). The baseline is 0 ms by design.

WATCH facts (node-redis 5.12, measured against `redis:8` in `app/test/chapter3.test.ts` and in the check; the docs digest says the exec
"rejects (WatchError)" and that matches):
1. After `WATCH k`, another connection changes `k`, then `multi()...exec()`: **`exec()` throws** (rejects); it does **not** return `null`.
   The error is an instance of `WatchError` (exported by `redis`), message `One (or more) of the watched keys has been changed`, but its
   **`name` is `"Error"`**, so `err.name === 'WatchError'` is false. A learner file recognises it with `err.constructor.name === 'WatchError'`
   (or the message), as the reference fixture does. Nothing in the MULTI ran (the other connection's value stayed).
   Not verified: whether a workspace file could `import { WatchError } from 'redis'` inside the app and runner containers (the fixture avoids it).
2. EXEC clears the watch even when it fails: the next `multi().exec()` on the same connection runs normally.
3. `multi()....execAsPipeline()` **ignores WATCH**: after a fired WATCH it still ran and returned `['OK']` (it is a plain pipeline, no MULTI/EXEC).
4. A `duplicate()` of the injected learner client is **closed** until the learner calls `connect()`: any command on it rejects with
   `The client is closed`. On the injected (shared) client `connect()` is a swallowed no-op, but on a duplicate it is the real thing
   (`packages/shared/src/learner/counting.ts`: `LIFECYCLE` is swallowed only when `swallow` is true, which is only the injected client).
   The app closes learner-made duplicates after the request (`ctx.close()`), so the learner never calls `close()`.
5. The runner path behaves the same: the same module run through `POST /run` (30 calls, concurrency 30, wallet 100, fee 10) gave 10 `true`,
   20 `false`, 0 errors, and the vitest case builds the context with `createLearnerDeps`, which is what the runner child uses. The fail-fast
   wrapper (`withAbortSignal` derived handle per command) does not break WATCH/GET/EXEC on the duplicate.
6. 50 parallel joins through the app (`xargs -P 50`), fee 10, wallet 100: exactly 10 `200`, 40 `402`, `wallet:u-000010` = `0`,
   `contest:9001:entries` = `10`. Each request opens its own connection, so this costs 50 connects; the retry loop needs about as many
   attempts as there are rivals, so the reference fixture allows 200.

## Other things worth knowing
- The vitest suite reads Redis and Postgres from `REDIS_URL` / `DATABASE_URL` if set, else from `.env.p07`. The check exports the
  quest-a02 ones (6397 / 5439) for its run; run `pnpm --filter @quest/app test` by hand with the same two variables if quest-p07 is not up.
  The check flushes quest-a02's Redis after vitest so the compose app starts from a clean ticker.
- `x-quest-instance` is the container hostname under compose (12 hex chars). `scripts/hit.sh` prints the first four and counts distinct full values.
- `scripts/hit.sh` reads `PROXY_PORT` from the environment first, then `.env`, then 3000. The check sleeps past the clock-minute boundary
  when needed, because the baseline limiter is a fixed window aligned to the minute.
- With `--scale app=2`, `allowed` is 10 per instance that gets at least 10 requests: 20 in this run. The spec band is 14 to 20.
- Reference fixtures: `app/test/fixtures/{leaderboard-top,leaderboard-add,leaderboard-rank,leaderboard-recompute,contest-join,ticker-publish}.js`
  (`leaderboard-top.js` is copied to `ch3/leaderboard.js`). Keys: `lb:contest:<id>` zset (member = team id string), `wallet:<userId>` string,
  `contest:<id>:entries` counter, channel `score:match:<id>`.
- `leaderboard-add.js` refuses to create members (`ZSCORE` first, then `ZINCRBY`), because the contract says `null` for an unknown entry.
