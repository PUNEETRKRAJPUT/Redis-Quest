# E-03 handoff: the engine follows replica, Sentinel and cluster targets

Signatures of `packages/shared/src/learner/target.ts` are exactly the spec's (unchanged since the first build), plus an exported
`TargetError` class (thrown by `parseTarget`). `createTargetClient` casts through `unknown` internally: without that, tsc
checking the three node-redis client types against each other took 1.5 GB and ran the Docker image build out of heap.

## What I did
- `target.ts` + unit tests (15), exported from the learner index.
- `engine/src/redis.ts` rewritten around a `Link` (one node-redis client of the right kind); `RedisManager` keeps `send`, `onUp`, `connect`, `cliSend`, `resetCli`, `isUp` and the `redis_disconnect`/`redis_reconnect` events, and gains `targetInfo()`, `switchTo(url)` (strict: refuses and goes back), `transaction(cmds)`, `openSubscriber()`. `engine/src/keytable.ts` (key positions from the server's own `COMMAND` reply). Mirror writes go through `transaction` (MULTI/EXEC on one node, one command after another on a cluster). Channel/key-expired event checks use `openSubscriber()` (fresh client for Sentinel/cluster).
- `GET/PUT /api/target`, `redis_target_changed`, `sentinel_failover`; UI switcher (`ui/src/panels/TargetSwitch.tsx`, wired into `TerminalPanel`); harness rule + docs; README field lines.
- **Engine fix beyond the spec:** `eventMatches` let the event's own `kind: custom` shadow a `kind` in `match`, so `match: { name: redis_target_changed, kind: cluster }` could never match. Now a `kind` in `match` reads the payload. Tested.

## Target format
`redis://host:port[/db]` (`rediss://` too), `sentinel://<masterName>@h1:p1,h2:p2,h3:p3`, `cluster://h1:p1,h2:p2[,...]`. Bad string: 400 `invalid_url`.

## Options per kind (node-redis 5.12.1, as passed by `createTargetClient`)
| option | single (`createClient`) | sentinel (`nodeClientOptions` and `sentinelClientOptions`) | cluster (`defaults`) |
|---|---|---|---|
| disableOfflineQueue | honoured | honoured (both master/replica and sentinel clients) | honoured per node client |
| connectTimeoutMs -> socket.connectTimeout | honoured | honoured | honoured |
| reconnectStrategy -> socket.reconnectStrategy | honoured | master/replica clients honour it; sentinel clients are created with `reconnectStrategy: false` by node-redis, so it is ignored there | honoured per node client |
| name | honoured (`CLIENT SETNAME`) | passed to node clients, not verified | passed to node clients, not verified |
| RESP | top level, honoured | top level, honoured | top level, honoured |
| clientSideCache | top level; honoured with RESP 3 | top level; pooled cache, RESP 3 only | top level; pooled cache, RESP 3 only |
The last three rows' "not verified" cells: I did not run those combinations live. The engine itself uses RESP 2, no cache.

## Cluster routing (`Link.sendCluster`)
1. First key from the `COMMAND` table (loaded once per connect; subcommands like `object|encoding` included) -> `cluster.sendCommand(firstKey, false, argv)`: node-redis picks the slot and follows MOVED/ASK itself (up to 16 redirections, rediscovers slots).
2. Commands flagged `movablekeys` (EVAL, XREAD, ...) ask `COMMAND GETKEYS` first, then route on its first key.
3. No key (INFO, DBSIZE, CLUSTER INFO/NODES/KEYSLOT, PING, CONFIG GET, KEYS, unknown commands): sent to **the master that owns slot 0** (deterministic; the spec said "a random node" for the unlisted ones, I used the same node for all so results repeat). `DBSIZE` and `KEYS *` therefore see one node only: `DBSIZE` answered 0 in the check although `game:*` keys exist elsewhere (a lesson, not a bug).
4. A server error (CROSSSLOT, MOVED that survives 16 tries, READONLY) comes back as the error line. `MSET a 1 b 2` -> `(error) CROSSSLOT Keys in request don't hash to the same slot`.
5. Not handled: SUBSCRIBE-family on the terminal for a cluster (mode reset only), `__keyevent` expired subscriptions on a cluster listen on one node only (not verified).
`GET /api/target` on a cluster: `nodes` is the number of nodes node-redis holds connections to (masters: 3), not the 6 of `CLUSTER INFO`.

## Sentinel
Commands go through `sentinel.sendCommand(false, ...)` (master). State up/down comes from a PING every 500 ms on the main link (node-redis follows a failover silently). `sentinel_failover` is emitted when the client's `MASTER_CHANGE` names a different master **and** the next probe PING succeeds, i.e. when the engine can really talk to the new master.
**Measured with node-redis 5.12.1, and A-05 reports the same:** with a reconnect strategy that never gives up, a Sentinel client is stuck in `connect()` to the dead master and never follows (the check's first attempts: CLI hung until its own 8 s reset). The engine uses a strategy that gives up after 2 retries and a 1 s connect timeout for Sentinel clients (`giveUpAfterTwo` in `engine/src/redis.ts`, not A-05's `reconnectStrategyFor`; same idea). Side effect: node-redis prints `ReconnectStrategyError` stacks to the engine's stdout during a failover. A dead master addressed by IP (not hostname) with the default 3 s connect timeout made the engine ~10 s late (about 16 s instead of 7 s).

## Event payloads
- `level.event` `{ kind: 'custom', name: 'redis_target_changed', data: { from: <old url>, to: <new url>, kind: 'single'|'sentinel'|'cluster' } }` on every successful `PUT /api/target` (not on a refused strict one).
- `level.event` `{ kind: 'custom', name: 'sentinel_failover', data: { masterName: 'mymaster', from: 'redis:6379', to: 'redis-replica:6379' } }`.
- `GET /api/target` -> `{ redisUrl, kind, description, state, master?, nodes? }`. `PUT` body `{ redisUrl, strict?: true }`; strict and unreachable -> 502 `target_unreachable` with the engine's message, and the engine goes back to the previous target (the UI sends strict). Without `strict` the old contract holds (200, `state: down`, keeps retrying).
- `PUT` also rewrites the mirror on the new target (the existing `commit()` does) and re-sets the welcome gift.

## Measured failover timeline (this Mac, Docker Desktop, shipped compose with `--replica-announce-ip redis`; sentinel `down-after 5000`, `failover-timeout 10000`)
Step | time
---|---
`docker compose stop redis` returns | 0.4 s
engine `state: down` | 3.5 s
Sentinel `+sdown` / `+odown` / `+switch-master` (sentinel log) | about 5 s / 6 s / 6.2 s
`sentinel_failover` event (to `redis-replica:6379`) | 7.3 s
CLI `SET` works again / `GET /api/target` shows the new master | 6.6 s / 7.5 s
`docker compose start redis` -> `role:slave` | 10.8 s (it is `master` first; Sentinel reconfigures it on its next INFO cycle)
`SENTINEL replicas mymaster` lists `redis:6379` | 10.9 s after start
let Sentinel settle 12 s, then `docker compose stop redis-replica` -> `sentinel_failover` to `redis:6379` | 7.7 s
`docker compose start redis-replica` -> `role:slave` | 0.4 s (its command line is `--replicaof redis 6379`)
Two runs (exploratory, before the check) gave 8.0 s and 8.7 s for the first event. **For the content author:** do not stop the new master within ~10 s of a rejoin: Sentinel needs a fresh INFO from the old master (about 10 s) or the failback aborts with `no-good-slave` and retries only after 20 s (seen once when I restarted too early). Before the compose flag landed, a restarted `redis` could come back with a new container IP and Sentinel never adopted it (both nodes stayed master); the flag fixed that.

## UI control
In the Terminal panel header: `data-testid="target-select"` with the five presets and "Custom...", an up/down dot (`target-dot`), the engine's `description` (plus `, master host:port` for Sentinel), error message `target-message`, and "The app and the runner follow within about two seconds." The header polls `GET /api/target` every 2 s. The prompt shows `host:port>` for a single node, `mymaster@<master>>` for Sentinel, `cluster>` otherwise. Unit-tested like E-01's switch (static markup + the function the select calls). Not tried in a browser.

## What I could not verify
- The UI switcher in a real browser (no DOM test env; static markup and logic only).
- Cluster node failure/failover (a master dying) through the engine: not tested; the cluster reconnect strategy is the keep-trying one.
- `useReplicas`, RESP 3, client-side cache on any target; `name` on Sentinel/cluster.
- Pub/sub event verifiers (`channel_message`) on Sentinel and cluster targets: `openSubscriber` creates a fresh client of that kind but I did not run a level through it.
- Full-repo `pnpm -r build` was not run by me (A-05's files); the Docker image build in the check does run it and passed.
