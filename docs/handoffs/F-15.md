# F-15 handoff: the stack serves the Next.js UI from its own compose service

## What I did
- **Image** (`docker/node.Dockerfile`): the build stage still runs `pnpm -r build` (so `next build` runs, telemetry off),
  then assembles `/ui-standalone` (`cp -a` of `ui/.next/standalone`, plus `.next/static` and `public/`, created empty
  because `ui/public` does not exist yet). It also deletes sharp and its 36 MB of libvips builds (the UI never uses
  `next/image`; Next loads sharp lazily) and the symlinks left dangling. The runtime stage copies it to
  `/srv/ui-standalone` (own folder: the standalone output has its own `node_modules`) instead of `ui/dist`.
  Still one image for engine, app, runner and ui.
- **Compose** (`docker-compose.yml`): new `ui` service, same image and `linux/arm64`, command
  `node ui-standalone/ui/server.js`, `HOSTNAME=0.0.0.0`, `PORT=3100`, `NEXT_TELEMETRY_DISABLED=1`,
  `NODE_OPTIONS=--max-old-space-size=256`, `mem_limit: 384m`, no host port, no volumes, no `depends_on`, a node-based
  healthcheck on `/`.
- **Proxy** (`docker/Caddyfile`): `/app/*` to the app as before; `/api`, `/api/*`, `/health`, `/ws` and `/internal/*`
  to `engine:4200`; everything else to `ui:3100`. `/internal/*` is routed because `scripts/grade/grade.mjs` posts to
  `/internal/metrics` through the proxy (the engine's only other non-/api paths are `/internal/app-config` and
  `/internal/metrics`).
- **Scripts**: `scripts/start` waits for both `/health` and `/` (200) through the proxy and reports each separately.
  `scripts/preflight.sh`, `scripts/stop`, `scripts/reset` needed no change (ui has no host port; stop and reset are
  `docker compose down [-v]`).
- **Docs**: PLAN.md memory budget (ui 384 MB), stack line and tree line; CLAUDE.md stack line plus a UI routing line;
  README service table (new `ui` row, proxy row reworded). README formatted with prettier.
- **CI** (`.github/workflows/ci.yml`): workflow-level `NEXT_TELEMETRY_DISABLED: "1"`. The jobs already build, lint,
  format-check and test every workspace package, ui included.
- **Engine**: not changed. It runs API-only because the image has no `ui/dist`.

## Design decisions worth knowing
- `ui` has **no `build:` section** and `pull_policy: never`. `up --build` builds the image through engine, app and
  runner, and `ui` reuses that tag. Reason: several existing checks override only engine/app/runner with their own image
  tag; a `build:` on `ui` would have made every one of them build and tag the default `redis-quest-node:latest`.
  Consequence: `docker compose up -d --build ui` on its own, on a machine that has never built the image, fails
  with "image not found"; build with `docker compose build` or `scripts/start` first.
- Those checks start explicit service lists that do not include `ui`, so nothing else about them changes (the proxy
  would answer 502 for pages in those stacks, as it did for the API before the engine existed).

## Surprises
- `ui/.next/standalone` with `outputFileTracingRoot` at the repo root traces sharp and both libvips variants (glibc and
  musl) even though nothing uses them: 36 MB.
- The old e2e compose override did not isolate the image tag, so P0-10 would have rebuilt the owner's tag.

## Next agent must know
- Pages are served by `ui:3100`; any new engine-owned path must be added to the `@engine` matcher in `docker/Caddyfile`
  or it will be answered by the UI's 404.
- If `ui/public` appears it is picked up automatically; the Dockerfile creates an empty one when missing.
- If `next/image` is ever used, remove the sharp prune in the Dockerfile.
