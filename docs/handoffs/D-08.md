## Decisions and surprises
- Tuning (measured with a scratch autoplayer under Node, 40 seeds, fallback deck): a player who never swaps loses
  about 12 of 88 clients (13.6 with a slow hand); one who always swaps loses about 0.4 (4 with a slow hand). With
  the live deck (13 commands, three swappable) the no-swap player loses 24 to 28 of 88. So the swap matters and is
  not mandatory. These numbers are a design check on the game's own model, not Redis facts.
- The third client of every round always brings a slow command that has a cousin, so the lesson shows in about two
  seconds of game time.
- The digest has no sentence that says "Redis runs every command one at a time". Rule R1 below is an inference
  from four lines that each say it for one case (scripts, KEYS, EXEC, the thread note). The cabinet says so.

## The rules of Be the Redis, and where each comes from

Digest line numbers are lines of `docs/redis-docs-digest.md` on this branch. "Server docs" means the text of
`COMMAND DOCS` as the engine serves it (`GET /api/command-docs`, docs/handoffs/E-06.md).

| # | Rule the cabinet shows | Source |
|---|---|---|
| R1 | Redis runs one command at a time; while it runs, the other clients wait. | Inferred from digest L300 ("script's execution blocks all server activities during its entire time"), L260 ("KEYS blocks server"), L270 (EXEC: "no other client's request served in the middle"), L42 (threads limited to deleting objects in the background and module blocking commands). No digest line states it for every command: not verified beyond those four. |
| R2 | A slow command delays every client behind it. | Digest L300 and L260. |
| R3 | The summary and the complexity on a card are the server's own words. | Server docs. Offline, a built-in copy of nine replies captured from redis:8 by F-22 (`ui/test/terminal.fixtures.ts`): get, set, hset, zadd, xadd, expire, keys, lpos, scan. |
| R4 | Which commands walk the whole key: HGETALL, SMEMBERS, LRANGE (all), KEYS, LPOS. | HGETALL O(N): digest L21, L108. SMEMBERS O(N): L98. LRANGE O(S+N): L87. KEYS: L260 and the server docs. LPOS: the server docs (O(N)). |
| R5 | Ticks: O(1) = 1 tick, O(log N) = ceil(log2(N+1)/6) capped at 4, O(N) = ceil(N/100) capped at 60. One tick = 0.1 s of game time. | A simplification. The shape (a walk costs more the bigger the key) is the digest's (L21, L98, L108); the numbers are the game's. The digest gives no real durations. The cabinet says "simulation, not a measurement". |
| R6 | Only the first bound in a complexity text counts ("O(1) for each field/value pair added..." is O(1)). | A simplification. |
| R7 | KEYS can be swapped for SCAN, SMEMBERS for SSCAN, HGETALL for HSCAN. | KEYS/SCAN: digest L260 ("SCAN: incremental, safe for production"), L22. SMEMBERS/SSCAN: L98 ("use SSCAN"). HGETALL/HSCAN: L103 lists HSCAN among the hash commands but does not say it replaces HGETALL: the pairing is a simplification. |
| R8 | One cursor call costs 1 tick and covers 500 items. | 1 tick: server docs for SCAN ("O(1) for every call"). 500 items: a simplification (L22 shows `COUNT 100` as an example; the default is not in the digest, not verified). |
| R9 | After each cursor call the client's next call joins the back of the line, and the client is patient again. | "Until you reach the cursor value 0" is digest L22. Joining the back and the fresh patience are simplifications. |
| R10 | Commands run in the order they arrived. | A simplification. |
| R11 | A client gives up after 5 seconds of waiting. | A simplification: the game's rule, not a Redis fact. |
| R12 | Score = clients served in time. A round is one minute. | A simplification: the game's scoring. |
