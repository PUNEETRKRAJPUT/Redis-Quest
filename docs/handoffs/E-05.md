## `interview.questions` (the contract)
```yaml
interview:
  minutes: 10
  rebuild_of: example-code-01-cache-aside
  questions:               # optional; 1..5 normal quiz verifiers; option ids unique across the list
    - { type: quiz, question: "...", options: [...], correct: ..., explanation: "..." }
```
- Schema (`packages/shared/src/levels/schema.ts`): `interview.questions` is optional and **only valid with `rebuild_of`** (with `pool`
  it is an error: `interview.questions: questions go with rebuild_of; a pool entry carries its own`). Same quiz shape as a pool
  entry's; the 1..5 and unique-option-id rules are now one shared `followUpQuestions(owner)` (pool messages unchanged; the
  `rebuild_of` ones say "an interview level needs at least one / has at most 5 follow-up questions" and "option id X is used by
  another question of this interview level", positioned at `interview.questions.N.options.M.id`). `Interview` type gains `questions?`.
  No loader change (a quiz needs no file).
- Engine: the questions are verifiers **after** the level's own `verify`. `GET /api/levels/:id` lists them (public form, no answers) at
  indices `verify.length ..`; `interview.questionsFrom` = `verify.length` (null without questions, as before); `verify` grades the
  level's checks then the questions (a wrong or missing answer makes the verdict wrong, exactly as for pools). Implemented once:
  `ownQuestions()` and the non-pool branch of `effectiveLevel()` in `engine/src/pool.ts`, the verifier list of `renderLevel()` in
  `engine/src/levels.ts`, `questionsFrom` in `engine/src/server.ts`. The UI needed nothing: it already renders any `questionsFrom`.
- Harness: `questions = interview.questions` for a `rebuild_of` level, answered by the pool code path (`poolAnswers`: all right for
  right/works_but_wrong, the first wrong for wrong); the row note says `N follow-up questions`.
- Docs: `levels/README.md` ("Interview levels": field line, YAML, a `questions` bullet), `docs/grading.md`.
- Tests: `packages/shared/src/levels/__tests__/questions.test.ts` (6), `engine/test/questions.test.ts` (9: payload, effectiveLevel,
  grading, GET route). Fixture: `engine/test/fixtures/scratch-e05/` (interview with two questions + two scratch ops levels).
- For C-POL: the schema was built and passed before anything else, as asked.

## Run ops under the harness
**Environment** (`--run-ops`): the `.sh` runs from the repo root with `process.env` plus defaults for `QUEST_API` (= `--engine`),
`PROXY_PORT` (= that URL's port), `QUEST_OPS_ROOT` (a temp folder whose `workspace` links to `--workspace` / `$G01_WORKSPACE`, only
when one of them is set) and a git identity with `commit.gpgsign=false` (when not exported). `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE`,
`COMPOSE_ENV_FILES`, `G01_*` are inherited from the caller (G-01.sh exports them with `G01_RUN_OPS=1`; the E-05 check passes them with
`env ...` for the run-ops stages only, so the other stages prove the old behaviour). Without `COMPOSE_PROJECT_NAME` the log line says
`docker compose acts on the DEFAULT project` and nothing is healed or scaled (as the spec).

**Sequence around one `.sh` solution:**
1. `start` (setup), run the script in its own process group (300 s, `QUEST_OPS_TIMEOUT_S`; a script with an attached `docker compose up`
   gets 20 s and SIGINT, which is what ch0-01's wrong one needs).
2. Engine `/health` must say redis and postgres up. If not and the project is isolated: `docker compose up -d --no-build redis postgres
   engine app runner proxy`; wait up to 90 s (`QUEST_OPS_HEALTH_S`); the row note says what happened ("engine /health was not answering
   when the script ended ... answered again after N s"). Then `/app/health` (60 s).
3. `answer`/`quiz`/events as usual, `verify`. **Rule: for a `.sh` solution under `--run-ops` the harness never fakes `service_scaled`**
   (no `grader-instance-2` pushes; the note says `service_scaled: real`); other events are produced as before.
4. After verify (isolated project): `docker compose ps -q app` count, then `docker compose up -d --no-build --scale app=1 app` and wait
   `/app/health` (note: `app had N instance(s) after the script; scaled back to 1`); `GET /api/target`, and if it is not
   `redis://redis:6379`, `PUT /api/target` back; if the engine had been down, `POST /api/progress/restore`.
   (The scale-back is after verify on purpose: the second instance is what the script made, and verify may look at it.)
Skips under `--run-ops`: "ops shell" lifts; "needs the compose profiles" lifts **only for a level with at least one `.sh` solution**
(ch5-09's solutions are `.js`: nothing would start its cluster, so it stays skipped; deviation from the spec's wording, on purpose);
"needs a real Redis outage" stays unless a `.sh` of the level runs `docker compose stop|kill redis` (none: ch5-01 kills `redis-nopersist`,
so it stays skipped).

## What surprised me / what the next agent must know
1. **`./scripts/start` cannot run next to another compose project's ports**: its preflight treats the grading ports (3650/3500, 6385, ...)
   as held by a stranger and exits 1 (the "redis-quest" label is hard-coded). So ch0-01's reference "fails" its script (`exit 1` is in the
   note) and still grades right, because the grading stack is already up (the level's checks, `game:engine:boots >= 1` and the
   `ui_connected` event the harness posts for a good solution, are true without the script). ch0-05's
   reference works (the stack is down when `./scripts/start` runs, so the ports are free). The harness's step 2 heals both. Not changed
   (`scripts/start`, `preflight.sh` are not mine). Consequence: ch0-01's wrong script (`up redis`) grades wrong only because the harness
   posts no `ui_connected` for a wrong solution, not because the engine is missing. Worth knowing before trusting that row.
2. After `docker compose down -v` the stack takes 15 to 17 s to be healthy again (postgres re-seeds); the 90 s budget is ample.
3. Compose gives the environment precedence over `name:` and `COMPOSE_FILE` over cwd defaults; the script's `docker compose` calls really acted
   on `quest-e05` (the scale script's own `docker compose ps --format '{{.Project}}'` printed `quest-e05` twice).
4. The default project `redis-quest` was not running on this Mac during the check, so its "untouched" assertion compares an empty
   snapshot with an empty snapshot; the real proof is the evidence files (project name printed by the scripts) and that every compose
   call carried `COMPOSE_PROJECT_NAME`. If you run it with the default stack up, the snapshot has teeth.
5. `docker compose up` with no `-d` in ch0-01's wrong script stops the containers it attached to when interrupted, so the harness's
   heal runs and the row note says so.
