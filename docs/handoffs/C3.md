## Expected values for level 06 and how I got them
I started a throwaway `redis-server` 8.2.1, ran the fixture's one `EVAL` (`for i = 1, 40000 do ZADD KEYS[1] ((i * 7919) % 100000) / 10 'ft-' .. i`), and read the answers
back with both `redis-cli` (`ZRANGE ... REV WITHSCORES`, `ZSCORE`, `ZREVRANK`) and the reference bundle's own functions through node-redis (so the numbers are the JavaScript
ones the verifier will see). 7919 shares no factor with 100000, so no two teams tie. Results, now in `expect`:
- `top(9001, 3)`: `ft-29284` 9999.6, `ft-11605` 9999.5, `ft-23210` 9999.
- `addPoints(9001, "ft-5", 100)`: ft-5 starts at 3959.5, returns 4059.5; `ZSCORE` 4059.5. `addPoints` for `ft-nobody` returns `null` and `ZSCORE` stays nil.

## Deviations and gaps (every one of them)
1. **Level 12 needed a works_but_wrong solution.** The schema requires every behavior-shaped `antipattern` to have a `works_but_wrong` solution, and the spec lists only two `wrong` ones for 12.
   I added `12-works-but-wrong-js-race.js` (loads a library named limiter so the library check passes, never calls it, does the bucket in JavaScript: the concurrency antipattern fires).
2. **The 2.2 rule, levels 02 and 07.** The spec puts `TTL between [1, 60]` in 02's behavior step and `TTL between [1, 604800]` in 07's redis verifier, and also wants the no-expire solutions to be
   `works_but_wrong`. Both cannot hold (a failing behavior or redis check makes the verdict `wrong`). The TTL checks are in the antipattern only; 02's behavior pins `GET ... = "15"` instead
   (which also fails the in-memory solution). `02-works-but-wrong-get-then-set.js` increments on every call (like INCR) so that `GET` reads "15" and it stays works_but_wrong.
   The 02 antipattern order is behavior, TTL antipattern, concurrency antipattern, because the concurrency fixture deletes `u-limit-1`.
3. **`PUBSUB NUMSUB` and `FUNCTION LIST` cannot use `matches`.** The engine's `matches` fails on any list reply (checked in `assert.ts` and then in the proof). Level 11 uses `oneOf` on
   `["score:match:m-041", 1|2|3]` (1 per app copy, so up to 3) plus `PUBSUB CHANNELS score:match:m-041` `contains`. Level 12 uses `exists: true` on `FUNCTION LIST LIBRARYNAME limiter`; the
   function name `tb_allow` is therefore not verifiable (the behavior verifier proves the code works, whatever it is called). Neither command needed `allowWrite` (both are on the allowlist).
4. **06 returns `{ teamId, points }`, not `score`**, per A-02's handoff and the baseline (the spec's level table says `score`; the binding-facts block and the handoff say `points`).
   `rank`'s `around` entries use `score`, as the handoff defines.
5. **Level 12 clears functions with `FUNCTION FLUSH`** in the behavior fixture, because a library persists across runs and would otherwise let `12-wrong-evalsha-only.js` pass after the reference ran.
   `FUNCTION DELETE limiter` would error when the library is absent. Nothing else in the game uses functions. The antipattern's fixture only deletes buckets, so the library stays after Verify.
6. **Level 06/14 behavior verifiers each reseed 40,000 members** (one EVAL, tens of milliseconds); traffic runs last, after the final reseed, as the engine orders it.
7. **Ticker drill with two app copies.** After level 1 there are two copies; `resubscribe` pauses only the one the proxy picks, and `GET /app/ticker/m-041` alternates. The drill therefore asks six
   times and prints one line per copy (one shows `received=2 gaps=1`, the other `received=4 gaps=0`). The story and teach say so. `PUBLISH` receiver counts show 2, then 1, 1, then 2.
8. Level 05 is a decision level, so there is no `show_me`; `docs` points at the rate-limiter and node-redis pages.

## Surprises
- `packages/shared/src/learner/deps.ts` `closeRedis()`: the 2 s `setTimeout` that calls `client.destroy()` is never cleared when `close()` wins the race, so each `duplicate()` the app closes after a request
  throws `ClientClosedError` from a timer two seconds later. The app and the runner child have `uncaughtException` handlers, so it is logged, not fatal (the proof swallows and counts them: 51 in this run).
  Level 09 makes it visible: every join opens a duplicate. Not mine to fix; worth a follow-up.
- The engine's `matches` assertion fails on list replies (deviation 3), and `equals: null` works for a nil reply (used in 06).
- `docs/grading.md` says bundle solutions are supported, so 06 and 14 (three slots each) should grade live; level 01 is an ops shell, so the harness skips it (`SKIPPED (ops shell)`), and its `service_scaled` event is only produced by the harness for the reference if you run it with `--run-ops` or by hand.
