# A-05 handoff: the app and the runner follow replica, Sentinel and cluster targets; `deps.redisCached`

## What I did
- **Shared learner code** (`packages/shared/src/learner`): `createLearnerDeps` builds its client with E-03's `parseTarget` and `createTargetClient`
  (redis, rediss, sentinel, cluster). New `createCachedRedis`, `clientIsReady`, `reconnectStrategyFor` (all in `deps.ts`, exported). Counting proxy:
  `fallbackDuplicate` option (a Sentinel client has no `duplicate()`). Fail-fast: `use` is exempt. `LearnerDeps.redisCached` added.
  Note: the cached client lives in `deps.ts`, not a new file, to stay inside "Files owned".

  (outbox, change consumer, ticker) and the `oncall.lookupTeam` baseline use the helper, `RequestScope.create` takes `redisCached` and `redisUrl`.
  Outbox failure warnings throttled to one per distinct message per 10 s.
- **Runner:** `redisUrl` validated with `parseTarget` (400 with the parser's words), child builds deps through the helper.
- **Fixtures/tests/check:** `app/test/fixtures/contest-join-cluster.js`; `kinds.test.ts` (shared), `app/test/targets.test.ts`, `runner/test/targets.test.ts`;

## What each kind supports (measured, node-redis 5.12.1)
| | single / replica | sentinel | cluster |
|---|---|---|---|
| app shared client, workers, slots | yes (replica: reads only) | yes, through the master | yes |
| `duplicate()` | native | **none in node-redis**; deps hand out a fresh Sentinel client | native |
| `watch` | yes | **no** (use `redis.use(fn)` to lease a connection) | **no** (the WATCH join cannot run) |
| `withAbortSignal`, `scanIterator` | yes | no | no |
| `isReady` | yes | yes | **none** (`clientIsReady` checks open + created node clients) |
| SUBSCRIBE / PUBLISH | yes | yes | yes, global (not sharded); `PUBLISH` returns the count on the node it hit, so 0 even when a subscriber hears it |
| cross-slot | n/a | n/a (MSET a b works) | `CROSSSLOT` |
| client-side cache (RESP 3) | yes | yes (pooled cache) | yes (pooled cache) |
Runner: all three through `redisUrl` on `POST /run`. The ticker needed no "not subscribed on a cluster" fallback: it works on a cluster.

## `deps.redisCached` contract
`RESP: 3`, `clientSideCache: { ttl: 0, maxEntries: 5000, evictPolicy: 'LRU' }`, created on first property read, connected on first command, shared by every
request on the instance (app: `RedisTarget.cached`, rebuilt on target switch) and by the job in the runner child (closed with the context).
One log line per client (`redisCached: <description>; RESP 3, client-side cache on (LRU, max 5000 entries, no ttl)`).
**Deviation from the spec:** it asked for the plain client on Sentinel and cluster; I measured that caching works and invalidates on both, so it is on for all three kinds
(if building the cached client throws, it falls back to the plain client with one line saying so).
**Counted?** No. Its calls are not in `redisCommands`: a hit never reaches the server. The server's `INFO commandstats` is the truth. `deps.redis` is still counted;
`deps.log` unaffected. Lifecycle calls (`connect`, `close`, ...) from learner code are swallowed; `duplicate()` throws a clear error. Command timeout as `deps.redis` (2 s).
Measured: of three `hGetAll` of one key, with an HSET from another connection before the third, `cmdstat_hgetall` rose by exactly 2 on single, sentinel (also after failover) and cluster.
On the replica target the app's cached reads were invalidated by the replicated write (+1, +0, +1).

## Measured error texts
- Replica `SET`: `READONLY You can't write against a read only replica.` (runner result error; app: HTTP 500 `slot_error`, same text in body and `x-quest-slot-error`).
- Cluster `MSET a 1 b 2` / `MGET a b`: `CROSSSLOT Keys in request don't hash to the same slot`.
- Cluster join MULTI (`wallet:<u>`, `contest:9001:entries`): `CROSSSLOT Keys in request don't hash to the same slot` when both slots sit on one master (u-a05-3, slots 8805 and 7573 on redis-c2); **`MOVED 7573 redis-c2:6379`** when the wallet is on another master (u-a05-1, slot 551). So the spec's "expect CROSSSLOT" holds only for same-master keys. The unchanged WATCH reference fails first on a cluster, with `conn.watch is not a function`, as it does on Sentinel.
- Hash-tag join (`{wallet:<u>}`, `{wallet:<u>}:joins:<contest>`, one Lua script because there is no WATCH): exactly 10 of 50 parallel joins, wallet 0, joins 10, on cluster and on Sentinel.
- Leaderboard references (top, addPoints, rank) and the outbox / change consumer / `applyChange` (single-key MULTI) all succeed on a cluster.

## Sentinel failover as the app sees it (stop `redis`, from the last run)
Sentinel itself needs about 6.3 to 6.9 s (5 s down-after, then election) before `+switch-master`. App, stop command issued at 0 ms: first failing learner SET at 386 ms
(`RedisCommandTimeoutError: Redis command set got no reply within 2000 ms (is Redis down?)`), learner SET stable again at 5163 ms, `/app/target` showing `redis-replica:6379` at 7319 ms
(earlier run: 7650 ms and 8144 ms). I did not explain why a SET succeeded before `/app/target` showed the new master (the 100 ms poll reads `getMasterNode()`).
**Important:** with a reconnect strategy that never gives up, the node-redis Sentinel client did not recover for 35 to 41 s after a failover Sentinel finished in 7 s
(it opens a connection to the old dead master inside `connect()`, which never settles). Hence `reconnectStrategyFor('sentinel')` gives up after 3 tries. node-redis prints a stack to stdout with `console.log` on each such give-up.

## Things the next agent must know
- `docker-compose.yml` (not mine): the `redis` service has no `--replica-announce-ip redis`. After it rejoins as a replica Sentinel knows it as both `redis:6379` and its IP; a later failover back to `redis` stalls for the 10 s failover timeout and Sentinel's blind reconfiguration makes the new master replicate itself (no master left). E-03's "failover back" dance and C5 will hit this. My check does one failover per run.
- The change consumer starts at the stream tail on every target switch (A-01 design), so entries published right after a switch are skipped.
- node-redis Sentinel and the 2 s command timeout: during a failover commands hang inside node-redis; only the fail-fast timeout turns that into an error for the learner.
- The check ran in `ENGINE_MODE=real` (E-03's engine accepted `cluster://`); the stand-in engine path exists but was not exercised.
