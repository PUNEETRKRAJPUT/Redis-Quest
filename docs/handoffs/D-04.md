## Assumptions I could not check
- Nothing was run, so none of this has executed: the app tests, the UI tests, the page in a browser, the proxy path.
- That Caddy passes the request header `x-quest-trace` to the app and the response header back unchanged (I read no
  Caddyfile; the app already sets `x-quest-slots` and `x-quest-instance` the same way; same origin, so no CORS
  `Expose-Headers` is needed).
- That the counter delta is a sound test for "this call was a command": `failFast` and `countRedis` both run
  synchronously up to the counter increment (read from `packages/shared/src/learner/{failfast,counting}.ts`), so a
  call moves `counters.redisCommands` before it returns. If a node-redis upgrade changed that, bars would be missing.
- Auto-pipelined commands in one tick (`Promise.all`) are separate calls, so they show as separate overlapping bars,
  not one. Only `multi()...exec()` and `execAsPipeline()` draw one bar (labelled `MULTI/EXEC xN`, `PIPELINE xN`).
- `deps.redisCached` is not traced (the counters skip it as well: a hit never reaches the server). A level 2.x
  solution that reads through `redisCached` will therefore show no Redis bar for a hit.
- Response shapes of `/app/players/:id/stats` (the `player_stats` row) are rendered generically; the player's
  own return shape decides what shows.
- The header name `x-quest-trace` is the same for request and response.
- The macOS file system is case-insensitive: component files are named `WaterfallView.tsx` and `SpreadView.tsx`
  so they do not collide with `waterfall.ts` and `spread.ts` (tsc found that collision).
- The trace wraps the counted deps inside `app/` instead of extending `countRedis` in `@quest/shared`, because
  shared is not a file this task owns. It still uses the counters themselves to classify commands, so there is one
  counting mechanism and no second list of command names (only a small regex of module namespaces, `json`, `ft`, ...,
  for the label). If you would rather have it inside shared, move `traceRedis` there and drop the delta test.

## How to verify
On a stack with chapter 2's stats level (use an isolated project, never the default one):
1. `scripts/check/D-04.sh` (type check, lint, the three test files, wiring). With a stack up:
   `QUEST_BASE_URL=http://127.0.0.1:<proxy port> scripts/check/D-04.sh` adds a live traced request.
2. `curl -s -D - -o /dev/null -H 'x-quest-trace: 1' $BASE/app/players/p-028/stats | grep -i x-quest-trace` shows the
   JSON; the same without `-H` shows no such header.
3. Open `/phone` (or the Phone tab in a level). Player screen with your code off: a spinner for as long as the
   slow `player_stats` query takes, the waterfall is one `db` bar (blue). Switch your cache-aside on (level 2.2)
   and refresh: badge says "Your code answered", the first request has a `db` bar plus Redis bars, the next ones
   only Redis bars and no spinner worth the name. "Refresh 20 times" shows fastest, median, 90th, slowest.
4. Stop Redis (level 2.10) with your code off or on: an error card with the status, not a blank screen.
5. Fixtures screen with the baseline: one `db` bar; with `prefetch.getFixtures` returning `null` on a miss the
   route answers 500 `slot_error`/contract error and the card says so.

## Decisions and surprises
### Screens (four routes that exist today, all GET, all read-only)
| Screen | Request | Slot | Built by level |
| --- | --- | --- | --- |
| Player | `GET /app/players/p-028/stats` | `cache.getPlayerStats` | 2.1, 2.2 cache-aside, 2.4 stampede, 2.5, 2.10 |
| Fixtures | `GET /app/fixtures` | `prefetch.getFixtures` | 2.7 fixtures must never miss |
| Board | `GET /app/leaderboard/1?limit=10` | `leaderboard.top` | 3.6 the real leaderboard |
| Live | `GET /app/ticker/m-041` | none (the provided subscriber) | 3.10 the ticker |

`m-041` and contest `1` are the ids the app's own tests use (`app/test/chapter3.test.ts`); `p-028` is the player
the chapter 2 levels use. The ticker answers 404 `unknown_match` for a match it does not know (the test uses `m-001`);
the phone shows that as an error card. Not checked: whether `m-041` is known on a fresh stack.

### The trace header (contract between app and UI)
Request header `x-quest-trace: 1`. Response header `x-quest-trace`, JSON, printable ASCII, at most 3500 chars:
`{"v":1,"total":12.3,"n":5,"e":[["r","GET k",0.1,0.4,"b",1],...]}`. Row = `[kind r(edis)|d(b), label, startMs from
the start of the request scope, ms, by l(earner)|b(uilt-in), ok 1|0]`. `n` counts every call, `e` is what fit
(oldest first), at most 400 rows are kept in memory. Who ran is the slot runtime's flag at the moment of the call:
the route's own queries and every baseline count as built-in. A call still pending when the response goes out is
closed at that moment and marked not ok.

### Other
- "You waited" is the browser's time, click to last byte; "Inside the app" is the app's own scope time. The
  difference is the proxy and the network on this machine. Both are labelled as measured on this stack.
- "Refresh 20 times" runs the requests one after another, not in parallel, so they do not queue behind each other.
- An older answer never overwrites a newer one (a run token), and leaving the screen cancels a running batch.
- Reduced motion: the spinner carries `ds-still`; the elapsed time still counts, so a still spinner is not a frozen page.
