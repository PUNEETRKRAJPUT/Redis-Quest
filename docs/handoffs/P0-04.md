## What surprised me
- `pg_isready` inside the container over TCP (`-h 127.0.0.1`) is the right readiness probe: the init-time server listens on the socket only, so a TCP answer means init finished. The spec's "time the init after the container reports ready" cannot be literal, so the printed load time is container start to ready, which includes init.
- `FATAL: the database system is starting up` appears in the log from the init-time restart and the probe; it is benign and the check ignores exactly that line.
- A plain `count(*) ... WHERE player_id = X` over 2.2 M rows was only about 100 to 150 ms, short of the target, so `player_stats` also joins to contest_entries and does a second last-5 scan. The function sets `max_parallel_workers_per_gather = 0` and `jit = off` so the number does not depend on Docker CPUs.
- Stars are always in their team's XI; p-101 is a bowler in the fiction, so his batting aggregates are zero.

## For P0-07 (the app)
- `GET /app/players/:id/stats` runs exactly `SELECT * FROM player_stats($1)` and returns the one row (columns: player_id, name, team_id, role, matches_played, innings_batted, runs, balls_faced, fours, sixes, dismissals, batting_avg, strike_rate, balls_bowled, runs_conceded, wickets, economy, selected_count, selected_pct, captain_pct, last5_selected_pct, last5_points, avg_team_points, last5_avg_team_points). Unknown id returns zero rows (the 404 / "not found" sentinel level in 2.5). numeric columns arrive from `pg` as strings; bigint counts too.
- Do not add indexes or cache in Postgres; the slowness is the lesson. Expect 170 to 300 ms per call single-threaded, more under concurrency.
- Outbox rows are written by triggers on players, teams, matches, contests (payload is full row as jsonb with the original column names, numeric as JSON numbers). Mark `published_at` when drained. Updates that change nothing still emit a row.
- Regenerating 002-seed.sql changes ids/values only if `generate.mjs` or `fiction/` change.
