## Schema decisions the plan left open (please review)
Starred items are the ones I most want the orchestrator to look at.

1. **(*) `traffic.baseline` means "graded relative to the baseline run", and the three `*_ratio_*`
   assertions require `baseline: true`.** The draft P0-09 spec reads `baseline: true` as "this run records
   the baseline". Those two readings conflict; P0-09 and this schema must agree before content is written.
   My reading: the engine records the baseline (unmodified app, same scenario) when none exists;
   `baseline: false` is for checks with only absolute metrics (`hit_ratio_gte`, `error_rate_lte`).
   `hit_ratio_gte` and `error_rate_lte` are absolute, not ratios against baseline.
2. **(*) `antipattern` checks describe the healthy state; a failing check is a hit** (PLAN.md section 4's
   example: `EXISTS game:leaderboard:list` `equals: 0`). So "check passes = good" holds for every
   verifier type, and `VerifierResult.passed === false` on an antipattern means works-but-wrong. Every
   antipattern check must carry a `message`.
3. **(*) Behavior extension: `repeat` and `expectCount`.** The spec's `concurrency` has no meaning with one
   call per assertion, and the plan's rate limiter ("10 of 100 through") and lock ("500 racers, one
   winner") levels cannot be expressed without counting. An assertion may set `repeat: N` (calls run with
   the verifier's `concurrency`, default 1) and `expectCount: { value, equals|gte|lte|between }`.
   `expect` with `repeat` applies to every call. At most one of `expect` / `expectError` / `expectCount`,
   optionally plus `sideEffect`; at least one of the four.
4. **(*) `antipattern` stays redis-shaped (spec), which leaves several plan antipatterns inexpressible**:
   3.3 "HMGET then HSET in JS, race fails", 3.6 "sort in JS", 4.7 "RPOP, lost on crash". Some can be
   recast as state checks after a behavior run (2.3 "writes the cache instead of deleting": `EXISTS` = 0
   after the update). If behavior-based antipatterns are wanted, the cleanest additive change is allowing
   `type: antipattern` to take behavior-shaped `assertions` as an alternative to `checks`.
5. Level ids: chapter ids are short for canonical dirs (`ch1-keyspace` has id `ch1`, `ch4b-on-call` has
   `ch4b`), enforced. Other dirs: the id must equal the dir name or its prefix before a dash, so example
   chapters use their full dir name (`example-cli`, level id `example-cli-01-hostel-scoreboard`).
   `chapter` in a level is that string id, not the number from PLAN.md's example (`chapter: 1`).
6. `chapter.yaml` `levels` lists full level ids; every level file must be listed exactly once, in file
   number order, and every listed id must have a file. Duplicate `NN` in one dir is an error. Gaps in
   numbering are allowed (so a level can be removed without renumbering).
7. Incident messages: `from` is a slug (cast slug or `you`), not validated against `fiction/cast.json`
   (keeps `levels/` independent of `fiction/`); `time` is a quoted 24-hour `"HH:MM"`, matching the cast
   dialogue in `fiction/cast.json`.
8. `brainstorm` must contain an option with id `not-redis` (PLAN 4b: "always includes not Redis") and at
   least one `is_reasonable: true`. "Free-text allowed" became "the learner always writes one line"; there
   is no field for it.
9. `solutions` differ by mode, so `LevelFile` is a discriminated union on `mode`. File modes:
   `{ reference: path, wrong: [{ path, expect, because }] }` with extensions checked (cli `.redis`; ops
   `.sh`/`.redis`; code `.js`/`.mjs`). Decision: `reference` is an option id or a list (normalised to a
   list, one per quiz), and `wrong` entries use **`option:`** instead of `path:` with `expect: wrong` only.
   Decision option ids are unique across all quizzes in the level, the reference must list exactly the
   correct options, and each wrong option must be an incorrect one.
10. `wrong` must have at least one entry (PLAN 5: "at least one known-wrong solution"). An `antipattern`
    verifier requires a `works_but_wrong` solution and vice versa.
11. Mode requirements: `decision` needs a `quiz`; `code` needs a `behavior` or `traffic`. Any mode may mix
    verifier types (the plan has `ops+decision`, `code+ops`), `mode` is the primary build mode.
12. `fixtures` (required, per spec) is a YAML file `{ steps: [setup steps] }` the engine runs before that
    behavior verifier, so every run starts from the same state. Validated with its own file positions.
13. Read-only rule is an **allowlist** (fail closed); container commands are keyed with their subcommand
    (`CONFIG GET` allowed, `CONFIG SET` refused). `allowWrite` can only be `true`, needs `reason`, and is
    an error on a command that is already read-only. Excluded on purpose: blocking/stateful commands
    (`XREAD`, `SUBSCRIBE`, `MONITOR`), `SORT` (has STORE; `SORT_RO` allowed), `EVAL`/`FCALL` (the `_RO`
    variants allowed), `SCRIPT LOAD`. `KEYS` is allowed (local data, verifier only). The list comes from
    my knowledge of the Redis command table, **not verified against the digest** (which does not list
    flags); P0-09 could cross-check at startup with `COMMAND INFO`.
14. Setup and fixtures: `FLUSHALL`, `FLUSHDB`, `SHUTDOWN` are refused, and any argument starting with
    `game:` is refused (CLAUDE.md reserves the prefix). Verifier checks may read `game:*` (chapter 0 does).
15. Reply comparison contract (documented in the README, to be implemented by P0-09, consistent with its
    draft): RESP2 values; `null` = nil; numeric expected values compare numerically against numeric string
    replies; lists element-wise; `exists: true` = not nil and not an empty list; `matches` is a JavaScript
    regex with no flags on the string form; `lengthGte` = list length or string length; `contains` = list
    element equality or substring. `equals` accepts string, number, null or nested lists, not booleans.
16. Command argv accepts YAML numbers and normalises to strings in the output type (`string[]`).
    `quiz.correct` is normalised to a list. The command name (`cmd[0]`) may not be templated.
17. Templating: any string in a level, inlined markdown, fixture file or `.redis` solution. Allowed:
    `player.id`, `player.name`, `level.id`, `chapter.id`, `env.NAME` with `NAME` matching `[A-Z][A-Z0-9_]*`.
    `\{{` is a literal `{{`; an unterminated `{{` is an error. `renderTemplate` never reads `process.env`
    (the engine passes `env`), and throws on unknown variables or a missing env value rather than
    rendering an empty string. `.sh` and `.js` solutions are not templated.
18. Paths are relative to the file they are written in, must be relative, forward slashes, and must
    resolve inside the parent of the chapter directory (`levels/` for real chapters).
19. Markdown `{ file: ... }` must be a `.md` file; only `story`, `teach`, `task` accept it (spec).
    `LoadedLevel.sources` records where each came from.
20. Discovery: the validator walks a directory recursively for `chapter.yaml`, skipping `_`/`.`
    subdirectories and `node_modules`; a `_` directory passed explicitly is searched. Any `.yaml`/`.yml`
    outside a chapter directory is an error; `.yml` is refused; files not matching `NN-slug.yaml` are refused.
21. Event kinds that need a match key: `channel_message` → `match.channel`, `key_expired` → `match.key`,
    `service_scaled` → `match.service`, `custom` → `match.name`. Plan items like 0.1 "UI reached redis" and
    0.2 "PING seen" become `custom` events.
22. Other bounds: `timeoutMs` 100 to 600000; `concurrency` 1 to 1000; `repeat` 1 to 10000; `xp` a positive
    integer; `min_redis_version` a quoted `"8.4"` or `"8.4.0"`; `docs` must start with
    `https://redis.io/docs/` and contain no whitespace; `show_me` snake_case; `slot` like
    `cache.getPlayerStats` (P0-07's registry names); scenario ids kebab-case (not checked against
    `scenarios/`, which is empty today).
23. No `unlocks` field (PLAN section 4 had one); `chapter.yaml` order is the progression. Empty optional
    lists (`setup: []`, `hints: []`, `docs: []`) are errors: omit the key instead.
24. Verdict: an empty result list is `wrong` (a broken run must never pass). Verifiers run in list order,
    so `antipattern` checks see the state left by earlier verifiers (the code example relies on it).
25. Error output: paths relative to the repo root (dir with `pnpm-workspace.yaml`); arguments resolve
    against `INIT_CWD` so `pnpm --filter @quest/shared levels:validate levels/x` works from the root.
    `(yaml)` is the path for syntax errors, `(root)` for whole-file errors. Missing required fields point
    at the nearest existing ancestor; unknown keys point at the key; template errors point at the variable
    itself, including inside block scalars and markdown files.

## What surprised me
- In YAML an unquoted value starting with `{{` is a flow map (`title: {{player.name}}` parses as a map
  with a map key). The validator adds "a value starting with {{ must be quoted in YAML" to that error,
  and the README says it up front. Expect this to be the most common authoring mistake.
- zod 4 skips an object's refinements when the object already has shape errors, so semantic errors
  (exactly one assertion, read-only) only appear once the shape is right. Per-check refinements are local,
  so one bad check does not hide errors in its neighbours. A bad `mode` hides the rest of the file's
  errors (the discriminated union cannot pick a variant).
- The `yaml` package prints a Node warning for complex keys during `toJS`; silenced with `logLevel: 'error'`.
- Tests live in `src/levels/__tests__/` (the spec puts tests under `packages/shared/src/levels/`, and
  `packages/shared/test/` is not an owned path), so `tsc` compiles them into `dist/levels/__tests__/`.
  Harmless (vitest ignores `dist/`), and they get type-checked as a bonus; excluding them needs a
  tsconfig change, which I did not own.
- Several facts I wanted for the ops example (`CONFIG GET`, `OBJECT ENCODING`, `MEMORY USAGE`) are not in
  the digest, so the examples avoid them. The examples use only commands the digest names.
- The tree changed under me: P0-02/P0-11 files were committed mid-task and P0-04 files appeared, plus
  edits to `.gitignore` and `.prettierignore`. None of those are mine.

## Follow-up 1 (after review)
Rulings applied: `traffic.baseline: true` = graded against a baseline the engine records itself with the
level's learner slots deactivated (README updated); healthy-state antipatterns and `repeat`/`expectCount` stand.

What changed (additive only; no existing level shape changed meaning):
- **Behavior-shaped antipattern.** `type: antipattern` takes exactly one of `checks` (as before) or
  `slot` + `fixtures` + `assertions` (+ optional `concurrency`). A failing assertion is the hit; every
  assertion in this shape needs `message`. Mixing shapes, or a partial behavior shape, is an error. The
  output type `AntipatternVerifier` is now a union; narrow with `'checks' in v` / `'slot' in v`. The loader
  resolves and validates the fixtures file for this shape too.
- **Absolute traffic assertions** `db_queries_lte` (integer, total Postgres queries in the run) and
  `p99_ms_lte` (milliseconds), neither requiring `baseline`.
- **`answer` verifier** (new type, kept separate from `quiz` so a quiz stays multiple choice):
  `{ type: answer, prompt, expected: { cmd, transform?: string|number|length }, compare?: equals|numeric_within,
  tolerance?, message }`. `expected.cmd` follows the read-only allowlist (no `allowWrite`) and templating
  rules; the command name must be literal; `numeric_within` requires `tolerance`, `tolerance` requires
  `numeric_within`, and `numeric_within` with `transform: string` is refused. Defaults: `transform: string`,
  `compare: equals` (as numbers when the transform is number or length). A failing answer is `wrong` in
  `verdict()`. Decision: a `decision` level still needs a `quiz`, because its `solutions` name quiz option
  ids; `answer` is for cli/ops levels (0.3, 0.4, 1.4). New type `AnswerVerifier`; `VERIFY_TYPES` includes `answer`.
- **Examples:** `example-cli` gained an `answer` ("What did ZREVRANK return for you?"). New level
  `example-code/02-token-bucket.yaml` (3.3): the token bucket from the digest's rate-limiter use case, a
  sequential behavior verifier (exactly 10 of 15 allowed), and a behavior-shaped antipattern (100 concurrent
  calls, at most 10 allowed). Solutions: Lua via `EVAL` (reference), allow-all (wrong), HMGET then HSET from
  JavaScript (works_but_wrong). New invalid case `invalid/antipattern-both-shapes`.
- Tests 56 to 65; README sections for both antipattern shapes, absolute traffic, `answer`, verdict rule.
- For P0-09: CI needs a typed answer for `answer` verifiers when replaying reference solutions; the natural
  source is running `expected.cmd` itself (reference) and a deliberately different value (wrong). Whether the
  token-bucket race reliably over-admits is unproven until P0-09 runs it (it should: node-redis sends the
