# F-22 handoff: a terminal that helps

## Headline
The completion popup, the syntax bar and the clickable commands in lessons are built and verified, but **they stay
inactive in the real game until the engine gets two small read-only endpoints** (below). Reason: sending `COMMAND
LIST` / `COMMAND DOCS` through `POST /api/cli` is not safe (evidence next). Everything else in the spec (frame,
history, warning card, send-to-terminal bus, type-ahead) works today.

## Safety finding: helper commands through POST /api/cli are NOT safe

Question: can a `COMMAND DOCS get` sent through `POST /api/cli` influence a verdict, an event, or anything the player
sees? Yes, in two ways. Evidence:

1. **A BUSY helper raises a level event that a verifier reads.**
   - `engine/src/server.ts:825-847` (the cli route) runs the command and then emits events from the *reply*:
     `cli.dangerous` (only for `KEYS FLUSHALL FLUSHDB MONITOR DEBUG`, `engine/src/cli.ts:142`, so a `COMMAND ...`
     helper never triggers it), `cli_ping` (PING only, `server.ts:832`), `redis_busy` when the reply is an error that
     starts with `BUSY` (`isBusyReply`, `cli.ts:179`; the event carries the label of whatever command was sent,
     `cliCommandLabel`, `cli.ts:171`), and `script_killed`.
   - `levels/ch4b-on-call/05-everything-froze.yaml:90-95` has the verifier `type: event, match: { name: redis_busy }`.
     The engine's event ring and `EventLog` (`engine/src/events.ts`, `engine/src/verify/events.ts`) hold it.
   - `COMMAND DOCS` is not allowed during a busy script: on the isolated dev stack `COMMAND INFO command|docs` gives
     flags `loading, stale` only (no `allow_busy`), and `docs/redis-docs-digest.md:300` says only `SCRIPT KILL`,
     `FUNCTION KILL` and `SHUTDOWN NOSAVE` are served while a script holds Redis. So a helper that needs docs it has
     not cached yet, sent while that level's script is running, comes back BUSY and **emits `redis_busy` without the
     player having run anything**. I did not stage a busy script to watch it happen (it would plant one on the shared
     dev stack): the chain above is read from code and from the server's own flags, not exercised.
2. **Helpers are visible to the player and to checks through `INFO commandstats`.** Every command on the terminal
   connection is counted server-wide: `cmdstat_command|docs`, `cmdstat_command|list`. Levels read that section
   (`ch4b-02:126`, `ch4b-03:108,111`, `ch4b-05:142`, `ch5-05:112`, `ch5-11:77,80,83`) and the lessons tell the player
   to read it by eye (`ch4b-01` lines 41-42, 74). None of today's patterns matches `command|...` (they look for
   `unlink`, `scan`, `keys`, `eval`, `latency|doctor`, `memory|doctor`, `client|pause`), so no existing verdict
   changes, but the player would find commands they never typed in their own commandstats.

Safe parts: there is no server-side terminal history anywhere in the engine (searched `engine/src`), the learner's
history lives only in the browser; and the `cli.dangerous` broadcast cannot fire for a `COMMAND` helper.

**What I did:** no helper command is sent through `/api/cli` by default. The UI asks a read-only engine endpoint
(`engineSource` in `ui/src/terminal/docs.ts`) that does not exist yet, and checks `GET /health` for
`commandDocs: true` first, so today it asks nothing and logs nothing.

### The engine endpoints needed (I may not edit the engine)
```
GET /health                         adds  commandDocs: true
GET /api/command-docs/names         -> { names: string[] }   the server's COMMAND LIST, verbatim (subcommands as "client|list")
GET /api/command-docs?names=a,b     -> { reply: [...] }      the server's COMMAND DOCS a b reply as nested arrays
                                                             (a map is a flat [key, value, ...] array; the engine's
                                                             verify/reply.ts normalizeReply output is what is wanted).
                                                             At most 20 names; unknown names are simply absent.
both, while Redis is down            -> HTTP 200 { available: false }   (a 4xx/5xx shows as a console error)
```
The engine should answer both from **one snapshot taken when Redis first comes up** (`COMMAND LIST` plus one
`COMMAND DOCS`; the whole core set is about 0.5 MB of redis-cli text, measured) and refresh it only when the target
switches to a different server, never on a timer and never per request. Then serving help touches Redis zero times
during a level, and the only `command|docs` count in commandstats is from engine start, before any fixture's
`CONFIG RESETSTAT`. A client for `Health` in `ui/src/types.ts` can add `commandDocs?: boolean`; I read it with my own
fetch because that file is read-only.

If the owner prefers to accept the footprint instead, the switch is one line in `ui/src/terminal/docs.ts`
(`docsStore()`): `new DocsStore(cliSource(api.cli))`. `cliSource` is written and unit-tested against real replies, just
not wired. The two risks above would then apply.

## What I built
- **Command knowledge (`ui/src/terminal/docs.ts`).** Names once per session, docs per command on first need, batched
  (a popup of eight rows is one request), cached for the session; failures are quiet and retried after 15 s; a
  command the server does not know is cached as missing. Parses both the redis-cli text and the nested-array JSON
  into one `CommandDoc` model (summary, since, group, complexity, arguments with tokens, oneof and block, subcommands).
  Nothing about a command is written by hand. Two scope filters over the server's own data: names that are not
  lowercase, contain a dot or start with an underscore are skipped (Redis 8 lists module commands such as `FT.SEARCH`,
  `VADD`, `ts.info` in the same list), and a command whose docs say `group: module` is dropped when they arrive.
  The project says no vector or AI content; vector sets are `module` commands in this server. Not a hint, a scope cut.
- **Completion (`complete.ts`, `Assist.tsx`).** First word: popup above (or below when there is no room) the prompt
  with name, the server's summary and group; exact match first, then shorter, then alphabetical (no popularity table).
  Container commands then complete subcommands (`CLIENT LIST`, `XINFO STREAM`, summaries from the parent's docs). A
  fixed-height bar under the terminal shows the documented syntax with the argument at the cursor highlighted and
  already-typed ones green; with options still possible it points at what the command needs next (`ZADD z` points
  at `score member`); long syntax scrolls the active argument into view with the command pinned. Tab accepts,
  Up/Down move (a `tick` cue), Esc closes until the word changes, clicking a row accepts.
- **Keyboard feel.** Only four keys are claimed and only while the popup is open (Up, Down, Tab, Esc); Enter never
  accepts and always sends what is typed; printable keys keep filtering. With no popup, Tab keeps its page job and
  moves focus on (the old terminal trapped it). Type-ahead: keys typed while a command is in flight or a pasted block
  is running are queued and replayed in order (before, they were dropped in the milliseconds the reply took).
- **History.** Up/Down as before, now `ui/src/terminal/history.ts` (pure, tested), persisted in `sessionStorage`
  (survives reload, not a new tab; blocked storage is handled).
- **Dangerous commands.** Same trigger and text; the warning is now a card in the transcript (accent bar, tinted
  surface, bold title) drawn with background colours because the DOM renderer does not draw box characters (my first
  version with `╭─╮` had gaps). `[warning] KEYS` stays in the first line (e2e looks for `[warning]`). Plays `pager`.
- **Chrome.** Frame on the design system: status light (turf pulsing, wicket down), title, the current target as a
  button that opens the existing target switcher (kept mounted while closed so the prompt still follows failovers),
  Clear button, mono font loaded before measuring (JetBrains Mono via `--font-mono`), 2px sky focus ring on the
  frame, theme from the tokens, 24-bit palette mapped. `height` = pixels (the terminal area, chrome on top) or
  `'fill'`. `data-testid="terminal"`, the group role and label, and the F-06 focus fix are unchanged. Also fixed: the
  first prompt used to be drawn on the same line as the intro text.
- **`/terminal` page** restyled (`data-ds`, display title).
- **Clickable commands (`markdown.tsx`, `terminal/bus.ts`).** An inline code span, or a line of a ```redis block, whose
  first word is in the server's command list gets a small send-to-terminal action; a leading `redis> ` prompt is
  dropped; other languages are never actions. The action reserves no space (it floats over the corner), shows on hover
  and keyboard focus, has an accessible name (`Send GET a to the terminal`). It puts the text on the terminal's line
  without running it and focuses the terminal; with no terminal mounted it copies to the clipboard and says so in a
  toast. Because it needs the command list, **it shows nothing until the engine endpoints exist**.
  The bus also has `onTerminalWanted(fn)`: if a screen that can reveal a terminal registers there (F-21's workbench
  could switch to its Terminal tab), text sent while no terminal is mounted waits 4 s and the terminal takes it when
  it mounts. Nobody registers yet, so today it is the clipboard.
- Lesson code styling moved to `ui/src/terminal/markdown.module.css` on the Night match tokens, with the legacy
  classes kept on the markup (`inline-code`, `codeblock`, `hljs-*`). A fenced block is styled through a
  `data-night` attribute because `markdown.test.tsx` pins `class="codeblock"` exactly.

## Not done or not verified
- **The engine endpoints** (above). Until then: no popup, no syntax bar, no chips in lessons; the key hints bar shows
  history and clear only.
- The popup and chips have only been driven against the stand-in endpoint, never a real one. Safari and Firefox,
  screen readers (the textarea gets `aria-controls`, `aria-activedescendant`, `aria-expanded`, and a polite live
  region announces the suggestions; not tried with a real reader) and the sound cues by ear are not verified.
- A helper answered BUSY (the finding) was reasoned, not staged.
- Multi-line input and a prompt that wraps past the terminal width: the popup column assumes a one-row prompt.
- Ordering (shortest first) is a choice; say if the owner wants alphabetical.

## Surprises
- Redis 8's `COMMAND LIST` includes subcommands (`client|list`) and module commands in their own case.
- xterm 6's DOM renderer has no custom glyphs: box-drawing characters leave gaps between rows.
- The old terminal dropped every key typed while a command was in flight; a burst after Enter lost its tail.
- While I worked, a Module-not-found for my CSS module showed in the dev log (the import landed seconds before the
  file); it cleared by itself.
- I used `POST /api/cli` on the isolated dev backend (port 3400) about 60 times to capture the fixtures
  (`COMMAND INFO`, `COMMAND LIST`, `COMMAND DOCS`); those calls are in that backend's commandstats.
