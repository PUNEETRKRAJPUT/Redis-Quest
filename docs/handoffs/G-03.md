# G-03 handoff: no check acts on the default compose project

## What happened
`scripts/check/P0-01.sh` ran `docker compose up -d redis postgres`, then `pnpm -r test` against those services,
then `docker compose stop redis postgres`, all without a project name. `docker-compose.yml` declares
`name: redis-quest`, so those calls acted on the stack the owner plays on. During the F-25 integration work the
script was run four times while his game was up:

- his Redis and Postgres containers were stopped after each run (the last time for about five minutes);
- the app and runner unit tests ran against his Redis and Postgres. They clean up after themselves, so almost
  nothing stayed: one key (`t8:a-not-int-xx`, from `runner/test/learner.test.ts`) and six `outbox` rows (an app
  test updates player p-028 and the CDC trigger writes a row each time).

What I checked on his data, read-only, before touching anything: the save file (`.progress/progress.json`, last
written two days earlier), `GET /api/progress` (same player, XP and passed levels), the save mirror (in sync),
every Redis key by prefix (only his chapter 1 keys, the engine's `game:*` keys, the one test key and two
`runner:example:*` keys that the workspace examples write), and the row count of every Postgres table against a
second stack built from the same seed (all equal except `outbox`, six rows against none, created between
05:44 and 06:17 UTC, the time of the runs). I started his two containers again, saved the six rows as JSON,
deleted exactly those six rows and the one key, and left the two `runner:example:*` keys alone because a
player can create them too.

## What I built
- `scripts/check/lib/isolate.sh`: `quest_isolate <id> <proxy> <redis> <postgres> <insight>` writes `.env.<id>`
  (gitignored), creates a scratch tree under `scripts/check/.scratch/<id>` (gitignored) and exports
  `COMPOSE_PROJECT_NAME=quest-<id>`, `COMPOSE_FILE` (base file plus `scripts/check/compose.isolated.yml`),
  `COMPOSE_ENV_FILES` and `ENV_FILE` (for `scripts/preflight.sh`). From then on every `docker compose` call in
  the script is isolated, bare ones included. Before returning it asks Compose which project and host ports a
  bare call would use and exits 99 unless they are its own. `quest_isolate_down` removes the project, its
  volumes, its scratch tree and its env file (the image tag stays so the next run reuses the layers).
- `scripts/check/compose.isolated.yml`: own image tag for engine, app, runner and ui; logs, workspace and
  progress mounts in the scratch tree.
- `P0-01`, `P0-02`, `P0-06`, `P0-08`, `P0-11` call `quest_isolate` first and no longer read `.env`, `./logs`,
  `./workspace`, `./.progress` or the tag `redis-quest-node:latest`. `P0-11` removed the volume
  `redis-quest_insight-data` by name; it now removes its own project's volume.
- `scripts/check/G-03.sh` (Docker-free, has the `# ci: docker-free` marker so CI runs it): a static tripwire
  over every `scripts/check/*.sh`.

## Verified (commands and results)
- Guard, positive: after `quest_isolate guardtest ...` a bare `docker compose config` reports project
  `quest-guardtest` and image `quest-guardtest-node:latest`.
- Guard, negative: with the project name forced back to `redis-quest` the function prints
  `REFUSING TO RUN` and exits 99.
- `scripts/check/G-03.sh`: `G-03 OK` on the tree; run against the five original scripts from git it reports

## Surprises
- Starting from an empty Postgres volume exposed a readiness gap. The compose health check is
  `pg_isready -U quest -d quest`, which answers over the socket while the image is still loading the seed
  through its temporary server, so the container is "healthy" before the real server accepts connections.
  `P0-06` and `P0-08` failed on that the first time (they used to find an already seeded database in the default
  project). They now wait: `P0-08` for `pg_isready -h 127.0.0.1`, `P0-06` for the engine's `/health` to report
  Postgres up. Measured on this stack; not a claim about Postgres in general.

## Not done
- The compose health check itself is unchanged. A TCP check (`pg_isready -h 127.0.0.1`, with a start period long
  enough for the seed) would make "healthy" honest on a first start, and the engine would then wait for the
  real server. It changes the Postgres service definition, so it deserves its own task and a first-start test.
- The A-*, E-*, F-* and G-01 checks already scope their calls with `-p`; I did not convert them to the helper.
- `scripts/start`, `scripts/stop` and `scripts/reset` act on the default project on purpose: the learner runs
  them on their own game.

## What the next agent must know
- New check that needs Compose: `. scripts/check/lib/isolate.sh` then `quest_isolate <id> <four free ports>`
  before the first compose call, `quest_isolate_down` in the exit path. Pick ports no other check uses
  (`grep -rhoE "(PROXY|REDIS|PG|INSIGHT)_PORT=[0-9]+" scripts/check ui/e2e`; the five here use 4310 to 4350,
  6510 to 6550, 5610 to 5650 and 5710 to 5750).
- Never run a script that drives Compose before reading how it names its project.
