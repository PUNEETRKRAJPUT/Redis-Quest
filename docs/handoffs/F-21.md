Layout decisions: the brief holds beats 1 to 5, the scoreboard holds the check button (sticky at the top until the
level is passed), answers, hints, beat 6 ("The decision": verdict + checks) and beat 7 (the ideal way), so every
`stage-<n>` keeps its default open state ({1: true}) and its first-button toggle. The scoreboard keeps a result to
itself until the big screen reveals it, and the passed panel waits for the reveal too.

## Surprises / what the next agents must know
- `Button` from `@/design` takes no `ref`; `Hints.tsx` hands its buttons to refs through a `display: contents` span.
- `transition-colors` also animates `outline-color`, so a focus ring fades from currentColor to sky over 150 ms.
- Markdown blocks have no gaps inside `data-ds` (the legacy `.md p` margins are reverted); the brief adds a flow gap
  `[&_.md>*+*]:mt-[0.85em]`. If F-22 gives markdown its own spacing, this can go.
- The verify flow emits WebSocket events that the shell (F-17) turns into toasts ("Verify started", "Verify check
  finished", ...); during the review they stack in the corner and compete with the big screen. Suggest the HUD skips
  `verify_*` toasts while a level screen is open.
- EditorPanel's file list takes about half the editor width in a 550 px workspace; a collapsible file list (F-24)
  would give code levels much more room.
- A dev HMR update that lands during a review can drop the overlay for that one review (seen once while I edited
  BigScreen mid-run); not reproducible without an edit.
