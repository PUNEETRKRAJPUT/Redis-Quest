## Assumptions I could not check
- Everything in the next section. Nothing was run against a real Redis, so each house entry and each "can be beaten"
  claim is unproven.
- `CLIENT INFO` reports `db=<n>`; `MEMORY USAGE` answers an integer for a key and nil otherwise; `FLUSHDB` and
  `SELECT 7` work on the target; the server has more than 7 databases. None of these are in
  `docs/redis-docs-digest.md` (only "FLUSHALL/FLUSHDB sends null" for client-side caching appears), so all are "not
  verified". The scorer refuses to run unless `CLIENT INFO` says `db=7`, so a wrong assumption fails closed.
- node-redis: `createClient({ url, database, socket: { reconnectStrategy: false } })` selects the database on connect
  (types checked, behaviour not run), and `client.sendCommand(argv)` on a plain client returns the raw reply.
- The engine's Redis target when it is a single node is `redis://host:port`, so its URL can be reused for a second
  connection; a URL with a path or credentials is passed straight to node-redis (not run).
- Sentinel: the master address from `redis.targetInfo().master` is reachable from the engine as `redis://host:port`.
- The built shared `dist` is what `scripts/league/score.mjs` imports (`packages/shared/dist/index.js`).

### The six holes: house entry, the shorter entry, what it relies on, and the digest line that documents it
Digest line numbers are lines of `docs/redis-docs-digest.md`. "not verified" means the digest does not state it.

**01-kit-room (strings), par 5**
- House: `SET kit:bat 12`, `SET kit:ball 30`, `SET kit:pads 8`, `SET kit:gloves 10`, `SET kit:helmet 6`.
- Shorter, 1 command: `MSET kit:bat 12 kit:ball 30 kit:pads 8 kit:gloves 10 kit:helmet 6`.
- Relies on MSET: digest line 66, "MSET/MGET (O(N) keys, atomic)". The argument shape (key value pairs) is not in the digest:
  not verified.

**02-player-card (hashes), par 4**
- House: `HSET player:7 name "Meera Rao"`, `HSET player:7 team "Hostel Hawks"`, `HSET player:7 runs 412`,
  `HSET player:7 wickets 9`.
- Shorter, 1 command: `HSET player:7 name "Meera Rao" team "Hostel Hawks" runs 412 wickets 9`.
- Relies on variadic HSET: digest line 103, "HSET (variadic, returns count of NEW fields)".

**03-season-table (sorted sets), par 4**
- Setup (single-pair ZADDs on purpose, so setup relies on nothing beyond the commands' names):
  `ZADD lb:north 10 amit`, `ZADD lb:north 20 binu`, `ZADD lb:south 5 binu`, `ZADD lb:south 7 chet`, `ZADD lb:south 3 dev`.
- House: `ZADD lb:all 10 amit`, `ZADD lb:all 25 binu`, `ZADD lb:all 7 chet`, `ZADD lb:all 3 dev`.
- Shorter, 1 command: `ZUNIONSTORE lb:all 2 lb:north lb:south`.
- Relies on ZUNIONSTORE: digest line 112 lists "ZUNION/ZINTER/ZDIFF (+STORE; 6.2.0)". Not verified: the `numkeys`
  argument shape, and that the default aggregate is SUM (binu must come out as 25). ZADD with one pair: digest line 112.

**04-bench-to-xi (sets), par 4**
- Setup: `SADD squad:bench p1` .. `p4`, `SADD squad:xi p5` .. `p7` (one SADD each).
- House: `SMOVE squad:bench squad:xi p1` .. `p4` (four commands).
- Shorter, 2 commands: `SUNIONSTORE squad:xi squad:xi squad:bench` then `DEL squad:bench`.
- Relies on: SUNION with STORE variants, digest line 96 ("SINTER/SUNION/SDIFF (+ STORE variants ...)") and SMOVE (named on
  line 96); DEL, digest line 258. Not verified: the argument shape of SMOVE and SUNIONSTORE (`destination` first, no
  `numkeys`). The house entry's end state (`squad:bench` gone after the last SMOVE) relies on "removing last element
  deletes key (all aggregate types EXCEPT Streams)", digest line 91.

**05-match-feed (lists), par 4**
- Setup: `LPUSH feed:latest e1` .. `e5` (one each; head is e5).
- House: `LPUSH feed:latest e6`, `LPUSH feed:latest e7`, `LPUSH feed:latest e8`, `LTRIM feed:latest 0 4`.
- Shorter, 2 commands: `LPUSH feed:latest e6 e7 e8` then `LTRIM feed:latest 0 4`.
- Relies on variadic LPUSH: digest line 87 ("LPUSH/RPUSH (variadic ...)"), and LTRIM as the capped-list tool, digest
  line 88 ("capped lists via `LTRIM key 0 N-1` after push"). Not verified: that a multi-value LPUSH leaves the LAST value
  at the head (the check wants e8, e7, e6, e5, e4 from the front).

**06-flash-sale (expiry), par 8**
- House: `SET deal:N live` then `EXPIRE deal:N 60` for N = 1..4.
- Shorter, 4 commands: `SET deal:N live EX 60` for N = 1..4.
- Relies on `SET key value EX seconds`: digest line 259 (`SET key 100 EX 10`), TTL and EXPIRE on the same line. Not verified:
  that TTL answers 55 to 60 right after (the check accepts that range).
- Possibly 1 command with MSETEX (digest line 67: "MSETEX (8.4.0, shared expiry)"); its syntax is not in the digest and
  the docs are ahead of many images (the digest's own framing note), so not verified. The E-06 handoff measured
  `redis:8` with redis-cli 8.10.3, which makes MSETEX likely to exist; if it does, hole 06's best score becomes 1 and
  nothing breaks.

## Decisions and surprises
- `splitArgs` (engine/src/cli.ts) and the check evaluation (engine/src/verify/reply.ts, assert.ts) are copied into
  shared (`league/split.ts`, `league/evaluate.ts`) because the shared package cannot import the engine and the
  contributor script must run without it. Parity is pinned: `split.test.ts` repeats the engine's cases;
  `engine/test/league-parity.test.ts` runs both evaluators over 15 checks times 23 replies. A follow-up could move the
  originals into shared and have the engine import them.
- Scoring database is 7 (`LEAGUE_DB`): `game:*` is in database 0 and no level selects another database. The scorer runs
  `CLIENT INFO` first and refuses unless it reports `db=7`; it never flushes before that. The engine never scores on its
  shared connection: each run opens a connection of its own (`openScratch`), and runs are serialised.
- Beyond the spec's refused list, entries may not use SELECT, MOVE, SWAPDB, FLUSHDB, RESET, HELLO, AUTH, CLIENT,
  `COPY ... DB`, MIGRATE, transactions, blocking commands, SUBSCRIBE and friends, and some server-wide commands: any of
  them could leave the scratch database and write into the player's data, or never return.
- Tie-break bytes: `MEMORY USAGE` summed over every argument of every check that turns out to be a key (nil counts 0).
  "The keys the checks name" has no key-position table in shared, so this reads all arguments. Characters: the trimmed
  command lines joined by one newline.
- The house entry is the handle `par-house` (a reserved name in the README). `score.mjs` fails if a hole lacks one or if
  it does not take exactly par commands.
- Positioned errors: shared's levels loader keeps its zod-issue conversion private, so `league/loader.ts` has a small
  own version (unknown key, required, message). If a later task exports `zodErrors`, switch to it.
- The board is scored lazily by the engine on the first `GET /api/league` or score request and cached until a golf file
  or the target changes. When Redis is down or the target is a cluster, the holes still list, unscored, with the reason.
- The UI does not import `@quest/shared` (it has no such dependency); `ui/src/features/league/types.ts` writes the
  response shapes out.
- The workflow runs on `pull_request` only, never `pull_request_target`: an entry is contributor-written text.
- `ui/src/routes.ts` knows no `/league`, so the header's active link treats it as the map (read-only file; harmless).
