## Exact metric counting rules
`redisCommands` (proxy in `packages/shared/src/learner/counting.ts`):
- One command method call on the injected client = 1, counted when the method is invoked, even if the command
  later fails. This covers camelCase and UPPERCASE command methods, `sendCommand`, `scanIterator`-style helpers
  (the call counts 1, not once per SCAN page), `watch`/`unwatch`, `subscribe`, and module namespaces
  `json ft ts bf cf cms topK tDigest` (`redis.json.set` = 1).
- Auto-pipelining is not collapsed: `Promise.all` of 5 `incr` calls = 5.
- `multi()` and the chained commands count 0. `exec()` / `execAsPipeline()` counts 1 if at least one command was
  queued (so 0 for an empty or never-executed multi). Three commands in one MULTI = 1. `discard` resets the queue.
- Count 0: listener methods (`on`, `once`, `off`, `emit`, ...), `withAbortSignal`/`withCommandOptions`/`withTypeMapping`
  /`withFunctions`/`withScripts`/`asap`/`isolated` (they return a still-counted derived handle), property reads.
- Lifecycle `connect`, `close`, `quit`, `destroy`, `disconnect` called by learner code on the injected client are
  swallowed (resolve immediately, count 0) so one module cannot close a shared client.
- `duplicate()` returns a counted clone sharing the same counters; its own `connect/close` work normally and are not
  counted; it is closed by `ctx.close()` (error handler attached).
- Commands sent by anything other than learner code (the runner's own connect, `ctx.close()`) are not counted.

`dbQueries`: one per `db.query(text, params)` call, counted at invocation, including queries that fail. `db` is a
`pg.Pool` (max 10, connection timeout 3 s) wrapper; it returns exactly `{ rows }`.

Percentiles: nearest-rank over the per-call `ms` of this run, `p50Ms`/`p99Ms`, 0 if there are no calls; rounded to
0.001 ms. `errors` = calls with `ok:false`. `totalMs` = child wall time from start of the job to results (includes
connecting to Redis and loading the module). `calls` = number of results.

## Runner behaviour worth knowing
- `timeoutMs` (default 5000, clamped 100..60000) is the budget for the whole `/run`, not per call: each call gets the
  time that remains, calls not started in time fail with `TimeoutError`. An async hang therefore ends with a
  `TimeoutError` result in about `timeoutMs`; a synchronous infinite loop is SIGKILLed at `timeoutMs + 1000` and every
  call gets `KilledError`; `process.exit` gives `ChildExitError` ("exit code 3"). In crash cases the response also has
  an extra top-level `runError: { name, message }` (not in the spec; additive). Metrics counters are 0 in crash cases
  (the child died before reporting them).
- Module load failures (syntax error, no default export, missing file) fail every call with that error (`SyntaxError`,
  `LearnerModuleError`). Redis unreachable fails every call with the connection error (3 s connect timeout).
- Unhandled rejections and uncaught exceptions in learner code are caught in the child and written to `logs`
  as `[unhandledRejection] ...`; the call result is unaffected. `console.log` output of learner code comes back in
  `logs` as `[stdout] ...` / `[stderr] ...`. Logs cap at 1000 lines of 2000 chars.
- `/load` also runs in a child (importing executes top-level learner code). It returns `{ ok, exports, error? }`.
- Invalid requests (missing/escaping `module`, bad types) return HTTP 400 `{ ok:false, error }`. Limits: 10000 calls,
  concurrency 1..200.
- `redisUrl` / `databaseUrl` overrides work for a single-node `redis://` URL. Cluster URLs are not supported (node-redis
  needs `createCluster` with `rootNodes`); Chapter 5 will need that added. Not done.
- `runner/src/main.ts` stays the P0-01/P0-02 stub (prints `@quest/runner`, exits 0) unless `PORT` is set, in which
  case it imports `start.js` and serves. Compose sets `PORT=4100` for the runner service, so it serves there. I did
  this because P0-01 and P0-02 checks run `node runner/dist/main.js` bare and expect it to exit.

## Shared module API as built (`import { ... } from '@quest/shared'`)
```ts
createLearnerDeps(opts?: {
  redisUrl?: string;            // default env REDIS_URL, then redis://localhost:6379
  databaseUrl?: string;         // default env DATABASE_URL, then postgres://quest:quest@localhost:5432/quest
  log?: (line: string) => void; // receives deps.log(...) output, util.format-ed to one string
  redisClient?: LearnerRedis;   // reuse a connected client; close() will not close it
  dbPool?: pg.Pool;             // reuse a pool; close() will not end it
  connectTimeoutMs?: number;    // default 3000
}): Promise<{ deps: LearnerDeps; counters: LearnerCounters; close(): Promise<void> }>
// Async (not sync as sketched in the spec): the Redis client must be connected first.

loadLearnerModule(workspaceDir: string, relPath: string, exportName = 'default')
  : Promise<{ fn: LearnerFn; exports: Record<string, unknown> }>
// import(file URL + ?v=<mtimeMs>-<size>); throws LearnerModuleError for path escape, missing file, no export fn.
resolveWorkspacePath(workspaceDir, relPath): string   // throws if it escapes the dir

callLearner(fn, deps, args: unknown[] = [], opts?: { timeoutMs?: number })
  : Promise<{ ok; value?; error?: { name, message, stack? }; ms }>   // never throws; value is JSON-safe
runLearnerCalls(fn, deps, calls: { args?: unknown[] }[], opts?: { concurrency?; timeoutMs? }): Promise<LearnerCallResult[]>
aggregateMetrics(results, counters, totalMs): LearnerMetrics
percentile(sortedAsc: number[], p: number): number
countRedis(client, counters, opts?): client      // the proxy alone
toJsonValue(v), toLearnerError(e), LearnerTimeoutError, LearnerModuleError
types: LearnerDeps { redis, db, log }, LearnerDb, LearnerRedis, LearnerCounters, LearnerCallResult, LearnerMetrics, LearnerFn, LearnerError, LearnerContext, CreateLearnerDepsOptions, LoadedLearnerModule
```
The spec names the module `@quest/shared/learner`; `@quest/shared`'s `exports` only has `.`, so it is imported from
`@quest/shared` (P0-05's index also re-exports through the root). A subpath export would need a `package.json`
`exports` change, which is outside what I may edit.

## What P0-07 (the app, in-process on the request path) must know
- Copy the pattern, not the code: per learner call, `createLearnerDeps({ redisClient, dbPool, log })` with the app's
  own long-lived client and pool (so no connection per request), then `loadLearnerModule` -> `callLearner(fn, deps, args,
  { timeoutMs })` -> read `ctx.counters`, then `ctx.close()` (a no-op for passed-in handles). Counters are per context,
  so concurrent requests with their own contexts do not mix counts.
- In-process timeouts only abandon an async call; a synchronous infinite loop in learner code blocks the app's event
  loop and cannot be killed. Only the runner can do that. Decide in P0-07 whether slots with untrusted loops go through
  the runner.
- `loadLearnerModule` re-evaluates an edited entry file on every mtime/size change but Node can never evict old module
  versions, so a long-lived app leaks a little memory per edit; helper files imported by relative path are not
  cache-busted. Fine for a local game, noted.
- Run the app under real Node. Under vitest, `import()` with a query string is rewritten by the module runner and
  ignores the cache-busting; my loader test spawns a real `node` for that reason.
- Learner `quit/close/disconnect/destroy/connect` on `deps.redis` are no-ops by design, which is what protects the
  app's shared client. Learner code that calls `redis.duplicate()` gets a clone that `ctx.close()` closes.
- A blocking command (BLPOP etc.) on the shared client blocks that connection for everyone; give such slots a
  `duplicate()` or use the runner.
- Keys: `game:*` is reserved for the engine; my examples use `runner:example:*`.

## What surprised me
- `pnpm add redis` resolves v6 today; spec says v5, so the range is pinned to `^5.12.1`.
- A Proxy may not return a different value for a non-configurable own data property of its target. node-redis puts
  `json`, `ft`, ... on the client that way, so a counting proxy built directly over the client throws. The proxies now
  wrap an empty shadow object and forward to the real client.
- Vitest's module runner ignores the `?v=` query on dynamic `import()`, and `new Function('return import()')` fails under it
  ("dynamic import callback was not specified"), so the loader cache-bust test runs in a real node subprocess.
- A rejection left unhandled by the learner was not surfaced before the child replied; a 10 ms tick after the calls fixes it.
- Other agents' work is live in the tree: `pnpm -r lint` currently fails in `engine/` (unused vars in engine/src/server.ts
  and verify.ts); not mine, not touched. `pnpm -r build` passed.
- Compose `up -d` printed "Recreated" for redis and postgres on each run (compose config differs from the running containers
  after another task edited `docker-compose.yml`); harmless here.
