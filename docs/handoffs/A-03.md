# A-03 handoff: app work Chapter 4 needs (streams, job queue, credit, lock, jitter, Bloom, ops wall)

## Deviations from the spec (read first; C4 is built against this)
- **Route key rule.** The spec says "spaces and slashes replaced by `_`" but its own example is `GET_app_players_:id_stats`; a literal per-character replace gives `GET__app_players_:id_stats` (two underscores). I followed the example: **every run of spaces and slashes collapses into ONE underscore**, `route.replace(/[ /]+/g, '_')`. It is idempotent. `sample.route` that `ops.record` receives is the metrics route key `METHOD routerPath` (`GET /app/players/:id/stats`), so the learner applies the rule itself; `ops.range` accepts either form. Exposed as `routeKey()` in `app/src/workers/ops.ts` with a quotable comment.
- **The ops hook does not record two routes:** `/app/ops/wall` and `/app/ops/samples` (the wall's own reads and the manual sample route), so the wall does not chart itself. Every other counted request is recorded. Operational routes (`/app/health`, `/app/slots`, `/app/metrics`) were never counted.
- **Seven `jobs-*.js` fixtures, not six.** The slot table has seven job slots (enqueue, claim, complete, fail, reclaim, schedule, promote); the check text said six. All seven exist.
- **`balls` columns.** The baseline selects `"over", ball, batter_id, runs` (the real columns; `over` is a reserved word and needs quotes), not `over_no, ball_no`.
- **Added validation beyond the spec (none changes a contracted shape):** `POST /app/ops/expire-batch` refuses keys under `game:*` (400 `reserved_key`, the engine's prefix) and keys longer than 256 chars; job ids in paths and `worker`/`consumer` are at most 64 chars; `error` on fail at most 1000 chars; payload size is judged on `JSON.stringify(payload).length <= 4096` (400 `payload_too_large`); a missing `payload` is 400 `invalid_payload` (`null` is a valid payload).
- **`jobs.claim` baseline waits** (polls every 25 ms) up to `timeoutMs` before answering `null`, like the real thing, instead of answering at once.
- **`contest.claimLastSlot` baseline** ignores `userId` (it never looked at it); the registry signature still reads `(deps, contestId, userId)`.
- **`wallet.credit` baseline** for a user with no wallet row credits nothing and answers `{ credited: false, balance: 0 }`; the routes do not 404 on it.
- **`ops.range` contract** (enforced by `GET /app/ops/wall`): `{ route: string, buckets: [{ at, requests, errors: numbers, avgMs: number or null }] }`. `GET /app/ops/wall` defaults: `to` = now, `from` = `to - 15 min`, `bucket` = 60000; bucket 1000..86400000, at most 10000 buckets, `from < to`.
- **Stats route** `GET /app/jobs/stats` answers 500 `internal` when Redis is down (it reads Redis directly, as specified); the baseline slots still answer.

Everything else (slot names, files, signatures, return shapes, key names, the 16 routes and their status codes) is as in the spec table.

### The provided hook (`OpsHook`)
While slot `ops.record` is active, every counted request except the two ops routes calls it once, after the response is sent, never awaited by the request, with `sample = { route: 'METHOD routerPath', status, ms (3 decimals), at: Date.now() }`. **Sampling is every request** (no fraction). Cost: one extra learner context and one slot call per request (its Redis commands run off the request path and are not added to the request's counters; the check proves the players route shows 0 `redisCommands`). At most 500 calls are in flight; beyond that a sample is dropped (`OpsHook.dropped`). Learner errors are logged once a minute with a count (vitest proves 15 failing requests make at most one log line). The hook respects the slot's 10 s `SLOT_TIMEOUT_MS`. Not exercised under heavy load: the 500 cap never triggered in any test.

### Key rule (quote for the levels)
`routeKey(route) = route.replace(/[ /]+/g, '_')`: `GET /app/players/:id/stats` becomes `GET_app_players_:id_stats`, so the keys are `ts:requests:GET_app_players_:id_stats`, `ts:errors:...`, `ts:latency:...`. `td:latency` is global.

## Measured facts for the levels (node-redis 5.12.1, Redis 8.10.3; the first group is re-measured by the check on every run, section "measured facts")
1. **`XAUTOCLAIM`** (`redis.xAutoClaim(key, group, consumer, minIdleMs, start, { COUNT })`) returns `{ nextId, messages: [{ id, message: { field: value } }], deletedMessages: [ids] }`. `nextId` is `'0-0'` when the scan is complete (loop until it is). A pending id whose entry was deleted (`XDEL`) is returned in `deletedMessages` and Redis removes it from the PEL (no `XACK` needed): measured `{"nextId":"0-0","messages":[{...01},{...03}],"deletedMessages":["1700000000002-0"]}`. Raw `sendCommand(['XAUTOCLAIM', ...])` is the 3-element array `[nextId, [[id, [f, v, ...]]], [deletedIds]]`. `redis.xAutoClaimJustId(...)` gives `messages` as an array of ids. Each XAUTOCLAIM with bodies adds one to the delivery counter; JUSTID adds none (measured: 3 stayed 3).
2. **`XPENDING`**: summary `redis.xPending(key, group)` is `{ pending, firstId, lastId, consumers: [{ name, deliveriesCounter }] }` (note: the per-consumer `deliveriesCounter` there read 3 for three pending entries each delivered once, so in the summary it looks like the consumer's pending count and not a delivery counter; that is my reading of one measurement). Extended `redis.xPendingRange(key, group, start, end, count, { IDLE, consumer })` is `[{ id, consumer, millisecondsSinceLastDelivery, deliveriesCounter }]`. `XREADGROUP` delivery makes the counter 1; each `XCLAIM` adds 1 (measured 1 then 5 after four `XCLAIM`s). **Off-by-one trap for level 4:** a sweep reads the counter after its own `XAUTOCLAIM`, which already added one, so an entry delivered once and claimed four times reads 6 in the sweep, an entry delivered once and claimed three times reads 5.
3. **`XGROUP CREATE` on an existing group** rejects with message `BUSYGROUP Consumer Group name already exists` (error `name` is plain `Error`; match on the message). `XADD` returns the id string. `XREADGROUP` with nothing new returns `null`.
4. **`BLMOVE` on the fail-fast learner client** (a `duplicate()` of it, and also the injected client itself): the 2 s command timeout does not apply. On an empty list with a 3 s timeout it waited 3083 ms and answered `null`; no `RedisCommandTimeoutError`. The wrapper exempts blocking reads (`b[lrz]*`, `xRead`, `xReadGroup`); `XREADGROUP ... BLOCK 2500` on the duplicate answered `null` after 2507 ms. **But on the injected shared client a blocking call holds the connection**: a `GET` issued 100 ms later waited 1910 ms behind a 2 s `BLMOVE`. That is the reason the reference `jobs.claim` uses `redis.duplicate()` plus `connect()` (the app closes learner duplicates after the request). `BLMOVE ... 0` blocks for ever, so the reference uses `lMove` when `timeoutMs` is 0 (the route allows 0).
5. **Typed module methods exist and work** (through the learner client too, counting proxy and fail-fast wrapper included): `redis.bf.{reserve,add,mAdd,exists,mExists}`, `redis.cf.{reserve,add,exists,del}`, `redis.tDigest.{create,add,quantile}`, `redis.topK.{reserve,add,list}`, `redis.ts.{create,add,mAdd,range,info}`, `redis.json.{set,get}`, `redis.ft.info`. Not exercised: `redis.cms`, `TDIGEST.*` beyond create/add/quantile, `TOPK.*` beyond reserve/add/list. `sendCommand` works for all of them but answers raw replies: `BF.EXISTS` gives `1` (typed: `true`), `TDIGEST.QUANTILE` gives `["30"]` strings (typed: numbers; an empty digest gives `["nan"]` raw and `[null]` typed), `TS.RANGE` gives `[[ts, "value"]]` (typed: `[{ timestamp, value }]`), `TS.INFO` a flat list (typed: an object with `retentionTime`, `duplicatePolicy`, ...). Typed `ts.create` takes `{ RETENTION, DUPLICATE_POLICY: 'SUM', LABELS: {...} }`; typed `ts.range` takes `{ ALIGN: 0, AGGREGATION: { type: 'SUM', timeBucket } }`.
6. **`TS.CREATE` on an existing key** rejects with `ERR TSDB: key already exists` (error name `Error`), the same through typed and `sendCommand`. `BF.RESERVE` on an existing key: `ERR item exists`. `TDIGEST.ADD` on a missing key: `ERR T-Digest: key does not exist`. **`TS.MADD` on a missing key does not throw**: the reply array holds an `Error` object for that item (`ERR TSDB: the key is not a TSDB key`), so a learner who does not look at the replies loses samples silently; `TS.MADD` never creates keys (the digest says so). **`TS.MADD` applies items one by one**, so a retry must resend only the items that failed (the first version of the reference fixture resent all and counted 31 requests for 30). `BF.EXISTS` on a key that does not exist answers 0, no error, so a missing filter looks like an empty one and every name is "free" with `checkedDb: false` (the check shows it on the runner path).
7. Measured once on a throwaway `redis:8` container (not in the check): `TS.CREATE k` with no options gives `retentionTime 0` and `duplicatePolicy block` in `TS.INFO`; with `RETENTION 86400000` it gives `86400000`. With `block`, a second sample for the same key and the same millisecond is refused (error text not measured), which matters when a level feeds two samples with one `at`; the reference uses `DUPLICATE_POLICY SUM` on requests and errors and `LAST` on latency (the digest does not mention `DUPLICATE_POLICY`: "not in the digest", it is a real `TS.CREATE` option measured here).
8. `DELEX key IFEQ value` works on this server (`1`): the contest lock fixture still releases with the digest's Lua compare-and-delete so it also runs on older servers.
9. **Handle of seeded `u-000010`: `tariq.bhat75`** (from Postgres in the check). `quest.ghost99` is not a handle in the seed (the check confirms Postgres says not taken).
10. Baseline race (contest slot, one slot, 50 parallel requests through the proxy): over the eight runs of the check, try 1 produced more than one winner in 4 runs and a single winner in 4; every run that needed it reproduced on try 2 (winners seen: 2 or 3, counter ending at -1 or -2). So it reproduces, but not on every try at 50 parallel; the level's verifier uses 200 concurrent calls with `repeat: 200`, as C4 planned.
11. Baseline double credit: two calls with one key give two credits and two `contest_payout` ledger rows (`ref` = the key) in Postgres (the bug the level fixes, shown by the check).
12. `redis.eval(script, { keys, arguments })` works through the learner client; `redis.multi()...exec()` and `execAsPipeline()` as in Chapter 3. `redis.set(key, v, { NX: true, PX: 5000 })` answers `null` when not set.

## What C4 should know (fixtures and shapes)
- Learner file contract: default export, `({ redis, db, log }, ...args)`. Fixtures are in `app/test/fixtures/<name>.js` and copy to `workspace/ch4/<name>.js` unchanged (`points-consume`, `points-sweep`, `jobs-enqueue`, `jobs-claim`, `jobs-complete`, `jobs-fail`, `jobs-reclaim`, `jobs-schedule`, `jobs-promote`, `wallet-credit`, `contest-last-slot`, `sessions-jitter`, `username-taken`, `ops-record`, `ops-range`). They can be the reference solutions after trimming comments. Bundles: each slot has its own file, so a "bundle" solution must be copied to every file the slots name; the registry has no shared files (no `exportName` use).
- Job hash fields written by the fixtures: `id payload status attempts enqueued_at_ms claimed_at_ms claim_token worker completed_at_ms result last_error run_at_ms`. Statuses: `pending`, `processing`, `completed`, `failed`, `delayed`. Retry and reclaim re-queue differently on purpose: `jobs.fail` retry does `LPUSH` (back of the line), `jobs.reclaim` does `RPUSH` (next to be claimed).
- Complete and fail check **status = processing and token**: after a retry or reclaim the old token is still in the hash and only the status kills the old claim. A level that seeds a job by hand (`HSET queue:jobs:job:fixture-1 ...`) must set `status processing` and `claim_token` or complete answers `false`.
- `jobs.complete` also `LTRIM`s `queue:jobs:completed` to 50 and sets a 24 h `EXPIRE` on the hash (same for failed).
- `ops-record.js` writes `ts:requests:<rk>` (value 1), `ts:latency:<rk>` (ms) on every call and `ts:errors:<rk>` (value 1) only for status >= 500, plus `td:latency` (t-digest). All three series are created on first use with `RETENTION 86400000` and `LABELS kind <requests|errors|latency> route <rk>`. An errors series with no error has no samples (`TS.INFO` `totalSamples 0`) but exists. Hand-computed example from the vitest and the check: samples `(60000, 200, 10ms) (60500, 200, 30ms) (61000, 500, 50ms) (125000, 200, 20ms)` with bucket 60000 give `[{ at: 60000, requests: 3, errors: 1, avgMs: 30 }, { at: 120000, requests: 1, errors: 0, avgMs: 20 }]` (latency series is `LAST` on duplicates, so two samples in one ms keep the last).
- `ops.range` is `TS.RANGE ... ALIGN 0 AGGREGATION sum|avg bucket` times three, merged by bucket start; a series that does not exist is an empty answer.
- Engine's `GET /api/metrics` and level `show_me` were not touched.
