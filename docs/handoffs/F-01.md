# F-01 handoff: Caddy dynamic upstreams for the scaled app

## What changed and why
`/app/*` used `reverse_proxy app:4000`, which resolves once and pins idle upstream connections, so a keep-alive
client stuck to one instance after `--scale app=2`. P0-07 worked around it with `APP_MAX_REQUESTS_PER_SOCKET=1`
(close after every response). Now Caddy re-resolves `app` every second and round-robins per request, and the env
default is `0`, so keep-alive is back on.
- `docker/Caddyfile`: `/app/*` block replaced (engine route untouched).
- `docker/README.md`: Caddyfile line updated.
- `docker-compose.yml`: `app` environment only: `APP_MAX_REQUESTS_PER_SOCKET: "${APP_MAX_REQUESTS_PER_SOCKET:-0}"`.
  `app/src/config.ts` treats `0` as unlimited (`int(..., 1, 0, ...)`, and `server.ts` only passes the option when truthy).
  `app/` not edited.
- `scripts/check/F-01.sh` (new), `.env.f01` (gitignored, ports 3400/6394/5436/5544).

## Caddy directives used
- `dynamic a { name app; port 4000; refresh 1s; dial_timeout 1s }`: upstream list comes from an A lookup of the compose service name, refreshed each second, so scaling needs no reload.
- `lb_policy round_robin`: picks the next upstream per request, independent of connection reuse.
- `lb_try_duration 2s` and `lb_try_interval 250ms`: short retry window so a just-removed instance fails over quickly without hanging the request.

## Measured splits (40 requests each, scale app=2)
- One curl, 40 URLs, one connection (verified "Re-using existing connection"): 21 / 19.
- 40 separate curls: 20 / 20.
- Running app env: `APP_MAX_REQUESTS_PER_SOCKET=0` in both containers.
