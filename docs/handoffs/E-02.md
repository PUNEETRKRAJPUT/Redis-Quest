## Route contracts
All three are under `/api`. The guard is `verifier.begin(owner)`, owner = the player id, or `no-player` before one exists (same as the
baseline refresh route). A traffic run, a verification, a baseline refresh and `POST /api/levels/:id/slots` therefore exclude each other.

### `POST /api/load/start`
Body `{ scenario: string, durationSec: integer 1..30, connections?: integer >= 1 }`. `durationSec` is required.
- `202 { scenario, durationSec, connections, startedAt, endsAt }` (ISO strings; `endsAt - startedAt` is `durationSec` seconds).
- The run is autocannon from inside the engine against `APP_URL`'s origin, **no warmup, no baseline, no slot switching, no grading**. The
  scenario is loaded with `loadScenario` and the caps are the verifier's (`LOAD_MAX_CONNECTIONS`, `LOAD_MAX_DURATION_SEC`, `LOW_POWER`).
  `durationSec` above the cap and `connections` above the cap are **clamped, not refused**; the 202 body reports the effective values.
  `connections` absent means the scenario's own (after caps): 50 for `toss-time-100`.
- `400 invalid_scenario` (missing, not a string, or the loader's error such as `scenarios/x.yaml does not exist`), `400 invalid_duration`
  (missing, not a whole number, outside 1..30), `400 invalid_connections`. Every 400 releases the guard.
- `409 { error: 'verify_in_progress', message: 'a verification or a traffic run is already running' }` while a verification or a run is going.
- No baseline is read, recorded or touched (the check asserts `progress/baselines` stays empty).

### `GET /api/load/status`
`{ running, scenario, startedAt, endsAt, now, last }`. While idle `scenario`, `startedAt`, `endsAt` are `null`. `last` is the most recent
finished run (including a stopped one) or `null`: `{ scenario, requests, rps, p99Ms, errors, status5xx, finishedAt }`.
`requests` = completed responses, `errors` = 5xx + requests with no response, `status5xx` = 5xx only.
Additive to the spec: `now` (engine clock, ISO, so a countdown does not trust the browser's clock), `last.scenario`, `last.finishedAt`.
`last` survives until the engine restarts (in memory only).

### `POST /api/load/stop`
`{ stopped: boolean }`; `true` when a run was going. It calls autocannon's `stop()` and waits up to 4 s for the run to wind down (autocannon
notices at its next one-second tick), so `running` is false when it answers. Measured: a 20 s run stopped 2 s in was over 5.2 s after it started.

## Events (`level.event`, ring and WebSocket; all `kind: custom`, payload under `data`)
```json
{ "kind": "custom", "name": "load_started",  "data": { "scenario": "toss-time-100", "durationSec": 5 } }
{ "kind": "custom", "name": "load_finished", "data": { "scenario": "toss-time-100", "requests": 84, "rps": 16.73, "p99Ms": 3509, "errors": 0 } }
{ "kind": "custom", "name": "load_failed",   "data": { "scenario": "toss-time-100", "message": "..." } }   // extra: autocannon rejected
{ "kind": "custom", "name": "redis_busy",    "data": { "command": "PING" } }
{ "kind": "custom", "name": "script_killed", "data": { "command": "SCRIPT KILL" } }
```
`durationSec` in `load_started` is the effective (capped) one. `load_finished` also fires for a stopped run. A failed run emits `load_failed`
and **never** `load_finished`, so "you ran the traffic" cannot be satisfied by a run that did not happen. A level matches them with
`kind: custom` and `match: { name: load_finished, scenario: toss-time-100 }` (`name` is top level, the rest is looked up in `data`; a unit
test runs that through `eventMatches`). `command` is the first word upper-cased, except `SCRIPT` and `FUNCTION` keep their subcommand
(`SCRIPT KILL`, `FUNCTION KILL`).
- `redis_busy`: any terminal command whose reply is an error reply starting with `BUSY`.
- `script_killed`: `SCRIPT KILL` or `FUNCTION KILL` whose reply is the status `OK`. `NOTBUSY` or `UNKILLABLE` errors do not emit it.
- Left as it was: `cli_ping` is still emitted for any `PING`, including one that got `BUSY`.

## The terminal during a long script (measured, quest-e02, redis:8, default `busy-reply-threshold`)
Setup: `docker compose -p quest-e02 exec -T redis redis-cli EVAL "<20 s read-only loop of redis.call('TIME')>" 0` in the background, T0 = launch.
- `PING` through `/api/cli` sent at T0 + 1 s: **no reply for about 4.5 s, then `(error) BUSY Redis is busy running a script. You can only call
  SCRIPT KILL or SHUTDOWN NOSAVE.`, type `error`, at T0 + 5.9 s** (run 1: 5934 ms after T0, `ms: 4261`; final run: 6389 ms after T0, `ms: 4510`).
  It does not hang for 20 s. Redis does not read client sockets until the threshold has passed, which is why a command sent early waits for
  it. A command sent after that gets BUSY at once (`GET some:key`: 2 ms).
- The BUSY reply arrives as an ordinary error line, not a thrown 500 (`runCli` already mapped error replies; I added a test). The terminal's own
  8 s ceiling (`CLI_TIMEOUT_MS`) is never reached with the default 5 s threshold; with a threshold above 8 s the terminal would answer
  `no reply after 8s; the terminal connection was reset` (from the code, not measured).
- `SCRIPT KILL` through `/api/cli` -> `OK`, type `status`, 3 ms. The `redis-cli` that ran the EVAL then ended with `ERR Script killed by user
  with SCRIPT KILL...`. `PING` answers `PONG` afterwards and `/health` is `redis: up`, `boots: 1` again.
- The engine has **two** node-redis clients (`main` for the mirror, setup and verifiers; `cli` for the terminal), so a terminal command stuck
  behind the script does not queue the engine's own traffic behind it. During the script: `/health` 200 in about 90 ms but with `boots: null`
  (the `INCR` result is not available; `redis` still says `up` because that is connection state), `/api/chapters` 200 in 90 ms, `/api/progress`
  200 in 100 to 160 ms. **Engine-side Redis commands do stop working:** `POST /api/levels/:id/verify` of a cli level took 4131 ms (waiting out the
  threshold) and every check answered `an error: BUSY ...` (verdict `wrong`, counted as an attempt); `POST /api/levels/:id/start` once BUSY had begun
  answered `500 { error: 'internal', message: 'BUSY Redis is busy ...' }` in 96 ms because its setup commands failed. Everything recovers by itself after the
  kill. C4b levels should tell the learner to kill the script before verifying.

## Assertion semantics and feedback strings
- **`redis_per_request_lte: n`** (absolute, `baseline` may be false): `redisCommands / requests` from the app metrics the tap sums for the run
  window (health probes excluded, same window as `db_queries_lte`). Pass/fail text:
  `<r> Redis calls per request (<c> commands over <n> requests), needs at most <k>`, e.g.
  `1 Redis calls per request (92102 commands over 92102 requests), needs at most 0.5` and `Passed under load: 0 Redis calls per request (0 commands over 84220 requests), needs at most 0.5; error rate 0%.`
  No app metrics: `Redis calls per request: no app metrics arrived during the run, so this cannot be measured` (fails).
- **`redis_calls_ratio_lte: n`** (needs `baseline: true`, member of `BASELINE_RATIO_KEYS`, the schema says so otherwise): that per-request number
  divided by the baseline's. Text: `Redis calls per request ratio 0.333 (1 per request now vs 3 baseline), needs at most 0.5`. If the baseline made
  no Redis calls it fails with `Redis calls ratio cannot be computed (the baseline made no Redis calls to compare with)`, same rule as
  `db_calls_ratio_lte`. Both keys are in `TRAFFIC_ASSERTION_KEYS`, so `at least one of ...` counts them. Both can be 0 or more; `redis_per_request_lte: 0` is allowed.
- **`notContains: "text"`** (one of the ten-now-eleven assertion kinds; the "exactly one assertion" rule counts it; the schema refuses an empty string and a
  number): the negation of `contains`. String reply: passes when `text` is not a substring. List reply: passes when no element equals `text` (same equality as
  `contains`; it is not a substring test over elements). Nil passes (nothing to contain). An integer reply is read by its decimal form. An error reply or no
  reply fails like every other assertion. Feedback `<message> (expected no "<text>", got <observed>)`; for a **multi-line string** the observed part is the
  line that holds the text (`a line reading cmdstat_keys:calls=1,usec=2,...`), because INFO replies are cut at 120 characters when shown, otherwise the usual
  `formatReply`. Real example from the check: `KEYS still shows up in INFO commandstats. (expected no "cmdstat_keys", got a line reading cmdstat_keys:calls=1,usec=2,usec_per_call=2.00,rejected_calls=0,failed_calls=0)`.
- **`matches` with a negative lookahead works on an `INFO` reply** (tested live and in a unit test): `matches: "^(?![\\s\\S]*cmdstat_keys)"` in YAML. `matches` runs
  `new RegExp(pattern).test(reply)` with no flags and `.` does not match a newline, so the pattern needs `[\s\S]*` to look across lines (the form I tested); a `.*` would only look along the first line. Its failure text is the generic one (`expected something matching /^(?![\s\S]*cmdstat_keys)/, got "# Commandstats\r\n..."`,
  cut at 120 characters), which is why `notContains` is the better form; both are in `levels/README.md`.

## Harness rules (`scripts/grade/grade.mjs`, `docs/grading.md` "Events the harness produces"; good solutions only)
- custom `load_finished` (`match.scenario`, rendered as a template): before verify, `POST /api/load/start { scenario, durationSec: 5 }` (409: wait 2 s and retry,
  15 times), poll `GET /api/load/status` every 500 ms until not running (cap 40 s). The note carries requests, req/s, p99, errors. A non-202/409 answer prints
  `NOTE load_finished: ...`.
- custom `script_killed` and/or `redis_busy` (one dance for both): `POST /app/oncall/badges/recompute` without awaiting, sleep 5.5 s, `PING` through `/api/cli`, then
  `SCRIPT KILL` through `/api/cli`, then await the blocked request (cap 15 s). A 404 within the first second prints
  `NOTE script_killed: /app/oncall/badges/recompute not available (A-04 not merged)` and carries on. In this run A-04's route was present in the working tree and the
  dance worked end to end: `PING -> (error) BUSY ..., SCRIPT KILL -> OK, blocked request ended with 500`.
- `uiActions` no longer prints "produced by the solution itself" for these three names. Levels without these keys and events take the old path: example-cli 3/3 and
  example-code 6/6 PASS in the check. I did **not** run `scripts/check/G-01.sh` (it takes long and `scripts/check/G-01.sh` has someone else's uncommitted edit adding `ch4b-on-call`).
