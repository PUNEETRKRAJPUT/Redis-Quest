## Not in the digest (stated in levels, check before shipping)
Everything below I either measured against redis 8.10.3 in the throwaway container (the check proves most of it on every run) or reasoned; none is in `docs/redis-docs-digest.md`:
- 01: why `MAXLEN ~` is the cheap form (it trims in chunks and may keep slightly more than N); the digest only says `~` is the default and exact trimming is "only if needed". `XINFO STREAM` has `length`, `first-entry`, `last-entry`.
- 02: `xReadGroup` answers `[{ name, messages: [{ id, message }] }]` or `null`; the error text starts `BUSYGROUP` (measured in this node-redis 5.12.1).
- 03: the extended `XPENDING` row is `[id, consumer, idle ms, delivery count]`; typed `xAutoClaim` answers `{ nextId, messages, deletedMessages }` and `xPendingRange` has `deliveriesCounter`; `XAUTOCLAIM` itself adds one to the counter, so a count read after it includes that claim (the digest says only "increments on every claim").
- 05: the meaning of `lag` and `pending` in `XINFO GROUPS` (lag = entries in the stream not yet delivered to the group; pending = delivered, not acknowledged) and the field order of the reply; the digest says only "alert on lag and pending".
- 06: `~` trimming leaving 100 (not 87) on a 200-entry stream with default settings. `DEL` removes groups (consequence of removing the key).
- 07: `blMove` takes seconds (a float is fine) and answers `null` on timeout; `HDEL` of the token on reclaim and finish; the 3600 s expiry of finished job hashes and the history cap of 50 (the digest's demo uses 50 for the history; the expiry value is mine).
- 08: `SET ... NX EX` answers `OK` or nil, and inside a Lua script `redis.call('SET', ...)` is truthy or `false`; a day (86400 s) for the idempotency marker is my choice.
- 09: `ZRANGE key -inf now BYSCORE LIMIT 0 100` (the digest names `ZRANGEBYSCORE`); the race between two JavaScript promoters is shown by the check (500 in pending, five of five runs).
- 11: the definition of a fencing token (a growing number the resource checks and uses to refuse older ones; the digest only says "you should implement fencing tokens" and names Kleppmann's critique), and the paused-holder scenario (Kleppmann's argument, referenced, not quoted, by the digest).
- 12: Redis reorders the flags (`Ex` reads back `xE`, `KEA` reads back `AKE`).
- 13: that a shared deadline makes the removal work and the re-logins arrive together (reasoning from "Redis deletes on access or by background scan", which is in the digest); the jitter size is called a product choice and no percentage is given.
- 14: `BF.EXISTS` answers 1 or 0; `BF.RESERVE` on an existing key errors (the fixture DELs first); about 1.8 MB for a million items at 0.1% is arithmetic from the digest's 14.378 bits per item.

## Surprises

- Unescaped hyphens in TAG queries are a syntax error, which would have broken the spec's `h-c-02-2` search on day one of a tester playing.

- Retention trims relative to the newest sample: a test that records a sample stamped now next to a sample from 2023 loses the old one. The `at`-less `record` proof therefore uses a different route.
- `TS.MADD` reports a missing key as an error inside the reply array (A-03's fixture handles it), not as a thrown error; my reference creates series first instead.
