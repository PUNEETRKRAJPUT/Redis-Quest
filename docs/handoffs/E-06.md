# E-06 handoff: the engine serves Redis's own command docs from one snapshot

## What I did
- `engine/src/command-docs.ts` (new): `buildSnapshot`, `parseNames`, `pickDocs` (pure, unit-tested) and the `CommandDocs`
  class. `ensure()` runs `COMMAND LIST` and one `COMMAND DOCS` (no arguments) on the engine's main link (`redis.send`,
  not the cli route, no level events, no key writes) and keeps the result in memory, tagged with the target URL.
- `engine/src/main.ts`: creates `CommandDocs` and calls `ensure()` from `redis.onUp(...)`, registered before
  `redis.connect` so the first "up" is not missed. Passed to `buildServer` as `commandDocs`.
- `engine/src/server.ts`: optional `Deps.commandDocs`, `commandDocs: true` in `/health`, the two GET routes, and a 400
  `{ error: 'invalid_names', message }` mapping in the existing error handler. Routes never call Redis.
- `engine/test/command-docs.test.ts` (new, 14 tests), `scripts/check/E-06.sh`.

## Behaviour
- Snapshot validity is `snapshot.url === redis.url`. A switch to a different server hides the old snapshot at once
  (`{ available: false }`) and the new target's "up" takes a new one. A switch that fails and falls back to the
  previous target (`switchTo`) shows the first snapshot again without a refetch. A reconnect to the same server keeps it.
- A snapshot that finishes after the target changed is discarded, and `ensure()` re-runs for the new target.
- A failed attempt (down, BUSY, 8 s without an answer) logs a warning and waits for the next "up". No timer, nothing
  inside a request.
- Unknown names are absent. Subcommand names (`client|list`) are also absent from `reply`: the unfiltered
  `COMMAND DOCS` holds top-level commands only, with subcommands nested in the parent's doc, and the UI never asks for
  a `|` name. (Measured on this stack: Redis itself does answer `COMMAND DOCS client|list`; the engine does not mimic that.)
- Names are matched case-insensitively and returned under the server's own spelling (`GET` finds `get`; `VADD` stays `VADD`).

## Measured on this stack (redis:8, redis-cli 8.10.3)
- `COMMAND LIST`: 669 names. Unfiltered `COMMAND DOCS`: 447 documented top-level commands (modules included).
- Snapshot in memory: 351,553 bytes as JSON; heap delta 566 KB (node 24, `--expose-gc`, normalized copy only).
  Raw `COMMAND DOCS` as redis-cli text is 284,706 bytes. The engine logs these numbers once when it takes the snapshot.
- Nothing about `COMMAND LIST` / `COMMAND DOCS` is in `docs/redis-docs-digest.md`; every claim above is measured, not documented.

## Verified (all from this worktree)
- `pnpm --filter @quest/engine build`: clean. `pnpm --filter @quest/engine lint`: clean. `prettier --check`: clean.
- Whole engine suite `cd engine && pnpm exec vitest run`: 20 files, 235 tests passed. The existing engine tests use
  fakes (no Redis or Postgres needed); only my check talks to a real Redis.
- `scripts/check/E-06.sh`: exit 0, output below. It leaves no container and no scratch directory behind.

## Not done / not verified
- Not run against Sentinel or cluster targets: `ensure()` uses `redis.send`, which routes per target kind (cluster:
  the node owning slot 0), but only a single node was tried. On a cluster each server's own module set may differ.
- The UI was not run against the real endpoints; the byte-identical comparison is on `get` only.
- The BUSY (script running) path is covered by a unit test with a rejecting fake, not by a real busy Redis.
- No image build, no compose project, `docs/BUILD.md` untouched.

## Surprises
- `buildServer` fakes in other tests vary (some lack `onUp`), so the engine wiring lives in `main.ts` and
  `Deps.commandDocs` is optional; without it the routes answer `{ available: false }`.
- The UI fixture for `get` is byte-identical to what the engine's `formatReply` renders from the snapshot reply, so
  the "same shape as POST /api/cli" claim is checked directly, not only by eye.
