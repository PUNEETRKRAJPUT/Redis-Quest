## What it found on its first day (2026-11-22)
Nothing in the game. In the checks:
- `P0-12.sh` looked for `pnpm -r test` after the CI step had become `pnpm -r --no-bail test` that morning.
- `P0-04.sh` compared the regenerated seed as gzip bytes. They depend on the zlib in the Node that ran the
  generator: identical on the Mac, different on the runner. It compares the SQL now.
- `D-06.sh` expected 65 to 72 taught commands, a count made by hand without a Redis. The server says 100.
- Two unit tests that fail now and then on a slow machine, both older than the ten days, both fixed on `main`:
  the runner counted its hard kill from the spawn (`6e20a28`, a real fix in `runner/src`), and an app test
  waited on a value it had read while the slot was off (`67edc1f`).

## What it does not prove
- Anything about macOS: `scripts/preflight.sh`, `open`, Docker Desktop's bind mounts and its port forwarding.
  The whole `scripts/start` was run on the owner's Mac instead (`docs/DAYS.md`, "Verified on 2026-11-22").
- Anything that judges a time on the machine. The full grader stays a Mac check: the reference solutions of
  ch3-06 and ch4b-01 are held to an absolute p99 (60 ms, 100 ms) that this 4-CPU runner misses before the ten
  days as well as after, and ch2-02 and ch4-15 sit near a timing edge there. On the Mac the grader gives 316
  PASS, 0 MISMATCH on the merged code. Chapter 5 level 03's proof measures the disk: the runner gave a ratio of
  0.31 on one run and 0.48 on the next, where the proof accepts 0.1 to 0.35.
- How anything feels to play.

## What surprised me
- **File owners.** Docker Desktop lets a container write to any bind-mounted folder and lets the user delete
  what a container left. Linux enforces owners: the game's containers run as `node` (uid 1000) and `postgres`,
  the runner as uid 1001. Hence root and `umask 000` in `run-check.sh`, and `chmod -R a+rwX .` in the setup so
  that what a check copies into its scratch folders stays writable there.
- **A first start answers before Postgres is ready.** The containers report healthy, the engine and the UI
  answer, and for about half a minute the engine says `postgres: "down"` and the app's database routes answer
  500, while the seed loads. The probe waits for it. `scripts/start` does not: a learner who opens the game in
  the first half minute of a first-ever start can see that. Not new, and not fixed here (see G-03's handoff on
  a TCP health check for Postgres).
- **`sed -i ''`** appears once in the P checks (`P0-08.sh`), which is all the stand-in is for.
- The Mac runners (`macos-latest`) cannot run Docker at all, so `ci.yml`'s `mac` job will keep skipping itself.

## What the next agent must know
- `stack-probe.mjs up` writes: it creates a player and makes the engine empty Redis database 7. Fresh,
  throwaway stacks only.
- To try a change to the workflow without touching `main`, push a branch named `e2e/<anything>`: the workflow
  runs on it. The `gh` login on the owner's Mac cannot dispatch or re-run workflows on this repository.
- Do not "fix" `scripts/start` or the check scripts for GNU tools: `D-02.sh` fails if `scripts/start` loses its
  BSD spellings. Add a stand-in instead, and say in it what it stands in for.
- `P0-12.sh` wants `ci.yml` to keep its jobs `fast` and `mac`: new hosted jobs belong in `stack.yml`.
- The three jobs take about 5, 9 and 14 minutes and run on every push to `main`.
