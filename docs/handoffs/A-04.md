# A-04 handoff: the planted faults for Chapter 4b "On call" and the two repair slots

## Deviations from the spec (read first; C4b is built against this)
- **The Lua loop is bounded by `os.clock()`, not by `redis.call('TIME')`.** Measured on redis 8.10.3: inside a script `TIME` is frozen at the script's start (the same value before and after a 2,000,000-iteration loop), so a loop waiting on it never ends and only `SCRIPT KILL` stops it. That breaks "nothing can hang for ever". `os.clock()` (CPU seconds; one of the few library calls the Lua sandbox allows) works: a 1500 ms spin took 1.5 s of wall time. Still read-only (no `redis.call` write), so `SCRIPT KILL` works. `ONCALL_SPIN_MS` is read at call time, default 20000, clamped to 1 ms .. 120000 ms (non-numbers fall back to 20000). docker-compose.yml does not pass `ONCALL_SPIN_MS` to the app (not mine), so in compose the default applies.
- **The route does not surface the kill error; it answers the learner-client timeout.** The baseline calls `deps.redis.eval(...)`, and every command on the learner Redis rejects after `LEARNER_REDIS_COMMAND_TIMEOUT_MS` (2000). So `POST /app/oncall/badges/recompute` answers **500 `internal`, `Redis command eval got no reply within 2000 ms (is Redis down?)` after about 2.0 s**, long before the 5 s `busy-reply-threshold`, and long before the app's 10 s slot timeout (which only applies to learner code, not baselines). The script keeps running inside Redis. The killed EVAL's own error (`ERR Script killed by user with SCRIPT KILL...`) is measured by the check with redis-cli and is never visible through the app. If C4b wants learners to see it, the baseline would need a raw client, which the counting rules argue against.
- **Extra validation** (the spec's rules plus): count `prefix` refuses glob characters `* ? [ ] \` and also any prefix that is, or starts, `game:` including `g`, `ga`, `game` (they would match `game:*`); ttl-sweep `pattern` (1..128 chars) must start with literal characters and its literal head (before the first glob character) must neither start with `game:` nor be a prefix of it, so `*`, `g*`, `ga?e:x`, `[g]ame:*`, `?ame:x` are 400 `reserved_pattern`; views `userId`/`matchId` must match `^[A-Za-z0-9_.-]{1,64}$`; team ids the same; split `key` 1..256 chars. `registerRoutes` gained an optional 4th parameter `instance` (server.ts passes it) for `/app/oncall/status`.
- **Two env knobs not in the spec**: `ONCALL_SPIN_MS` (in the spec) and `ONCALL_LEAK_CAP` (default 2000; the vitest sets 5 so the cap can be seen without opening 2,000 connections).
- **Leak cap as built**: after 2,000 leaked clients (spec value) each new one closes (`destroy()`) the oldest, and logs one warn line a minute (`oncall.lookupTeam leak cap reached`). A failed connect is destroyed, not leaked. A lookup for a missing team still leaks its client (the 404 comes after the connect). `closeOncallLeaks()` runs at shutdown. The cap path was only exercised with a cap of 5 (vitest), never at 2,000, and the app's memory at 2,000 leaked clients was not measured.
- `oncall.splitBigKey` reference fixture buckets by **32-bit FNV-1a of the field name modulo `buckets`** (application sharding, not a Redis hash slot). A first try with a 31-multiplier hash left the 64 buckets 1,261 to 8,306 fields apart on f1..f300000; FNV-1a gives 4,644 to 4,729. Splitting spreads the work per key; it does not change the encoding (each bucket is still `hashtable`, 4.7k fields > the listpack limit).

Everything else (slot names, files, signatures, return shapes, the seven routes and their codes) is as in the spec.

## Measurements (redis 8.10.3, arm64, Docker Desktop; the numbers below are from the check runs, re-measured on every run)
- **BUSY timing.** A `redis-cli PING` sent 0.4 s after the route was called is not answered until Redis starts refusing: it answers `BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.` **5,041 to 5,054 ms** after the route call (`busy-reply-threshold` is 5000 ms here). `SCRIPT KILL` then answers `OK`, PING answers `PONG` straight after. The killed EVAL's own error: `ERR Script killed by user with SCRIPT KILL... script: <sha>, on @user_script:1.`
- **What the app's other routes did during the freeze** (taken just after BUSY appeared, with the script still running): `GET /app/players/p-001` (Postgres only) HTTP 200 in 4.7 to 9.8 ms; `GET /app/health` 200 in 1.8 to 2.4 ms and still reports `redis: up` (the client is connected, just stuck behind the EVAL); `GET /app/oncall/users/count` (a `KEYS` through the learner client) **500 after 2,003 to 2,013 ms**, `Redis command keys got no reply within 2000 ms (is Redis down?)`. The route that started the freeze answered 500 after 2,004 to 2,010 ms with `Redis command eval got no reply within 2000 ms`. Every command on the app's shared client queues behind the EVAL on its one socket. Ticker and outbox workers: **nothing**. The app log held only the two `request failed in app code` lines (level 50, the two 500s) and no `unhandled` line; the ticker is idle and the outbox is off when no slot needs it, so neither made a Redis call in the window (not tested with the ticker or outbox active). Afterwards the app recovered with no restart: the next count call answered 200.
- **lookupTeam leak.** 200 requests, 100 in parallel through Caddy: `connected_clients` **9 -> 208** (+199), all 200 answered 200. Sampled every 20 ms from the first request: +50 after 206 to 323 ms, +100 after 426 to 756 ms, +150 after 603 to 1,018 ms, peak 208 or 209 (quiet machine; 200 requests took 0.78 to 1.3 s). `/app/oncall/status` reported `leakedClients: 202` (two earlier lookups included). `docker compose restart app`: `connected_clients` **208 -> 6** and `leakedClients` 0. The repaired slot (shared client): 100 lookups at 25 parallel left `connected_clients` at 6 -> 6.
- **KEYS over 200,000 keys** (`SET oncall:user:<i> x` by one EVAL): the `SLOWLOG GET` entry for `KEYS oncall:user:*` shows a server-side duration of **17,750 to 23,342 us (about 18 to 23 ms)** against the default `slowlog-log-slower-than` of 10,000 us, so it is logged, but only by a factor of two: a much faster machine could miss the threshold and fail that check line. Through the app, `GET /app/oncall/users/count` took 63 to 143 ms per call; the SCAN repair took 210 to 226 ms (more round trips, but it never blocks Redis) and left no `keys` entry in `SLOWLOG`.
- **The 300,000-field hash** (fields `f1`..`f300000`, values `v1`..`v300000`): `MEMORY USAGE` **16,869,331 bytes (16.1 MiB)**, `OBJECT ENCODING` **hashtable**. After the split into 64 buckets: 4,644 to 4,729 fields each, one bucket `hashtable` at 264,483 bytes; the repaired split of the whole hash took 680 to 1,018 ms through the route. `INFO commandstats` shows `cmdstat_unlink` after it.

- The oncall routes with Redis down, and any of this under `--scale app=2` (`leakedClients` is per instance by design; Caddy round-robins).
- Whether the ticker or outbox logs anything during a freeze when they are active (idle in the check).
- The route-level behaviour with a `SLOT_TIMEOUT_MS` under 2 s for learner code (not exercised).
- `ONCALL_SPIN_MS` through compose: the compose file does not pass it, so a level that wants a shorter spin needs `docker-compose.yml` to forward it (not my file).
- The hot-key level reuses `cache.getPlayerStats` and needs nothing here, as the spec says; not exercised.
