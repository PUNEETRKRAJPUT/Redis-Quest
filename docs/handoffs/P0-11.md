## Exact API requests (Insight 3.x, agreements spec 1.0.6; found via /api/docs-json)
```
GET   /api/health/                       -> {"status":"up"}
GET   /api/settings                      -> "agreements":null on a fresh volume
PATCH /api/settings   Content-Type: application/json
      {"agreements":{"eula":true,"analytics":false,"notifications":false,"encryption":false}}   -> 200, agreements echoed with version 1.0.6
GET   /api/databases                     -> []
POST  /api/databases  Content-Type: application/json
      {"name":"Redis Quest","host":"redis","port":6379}                                         -> 201
GET   /api/databases/{id}/connect        -> 200 (used by the check)
```
Idempotency is by exact name match on `GET /api/databases` before the POST.

## Surprises and decisions for the orchestrator
- There is no separate agreements endpoint beyond `PATCH /api/settings` (plus read-only `GET /api/settings/agreements/spec`). A fresh volume reports `agreements:null`; one PATCH with all four keys fixes it.
- DECISION: `eula:true` accepts Insight's Server Side Public License on the learner's behalf. The spec requires it; the learner should be told (suggest a line in the README/start script output).
- The POST response has `"new":true` on the database; whether the UI shows a "new" badge was not checked.
- The check removes only the `redis-quest_insight-data` volume to prove a first run works from nothing. A learner who previously used Insight keeps their volume (and any extra databases).
- `curlimages/curl:latest` is unpinned, like the other images in the project.
- Uses the compose network name `redis`, container port 6379, so a local port override in .env does not affect it.
